## Summary

Cached Supabase images are now admitted by a receipted image ID, so the SQL qualification jobs stop pulling from public.ecr.aws on every run.

## Problem

main went red after #765 (run 38816057620, 422189ce): `ovd591-retention-qualification / retention-sql` failed at `node scripts/ovd591-ci-fixture.mjs run-retention`. Artifact `ovd591-retention-38816057620-1` shows `fixture-result.json` `stage: "image"`, `failure: "image-pull: registry public.ecr.aws rate-limited after 5 attempts (budget 300s)"`. Every attempt hit `toomanyrequests: Data limit exceeded`. The SQL never ran, so #765's OVD-722 actor column and kill-RPC changes were not the cause. A rerun of the failed jobs passed. The same throttle failed capability-sql, free-quote-sql and retention-sql on #768, #755, #756 and #773.

The workflows already `docker save`/`docker load` the images through actions/cache. But a loaded image has no RepoDigests, so `pullFixtureImage({ skipLoaded: true })` never treated it as cached and pulled from ECR anyway.

## Acceptance criteria addressed

- [ ] A cache-hit run admits the loaded image without a registry pull (receipt `status: "cached"`, `source: "image-cache"`).
- [ ] A cache-miss run pulls as before, then receipts and saves the image.
- [ ] An image-ID mismatch falls back to a normal pull; admission guarantees are unchanged.

## Files changed

- `.github/workflows/{ovd591-qualification,ovd591-retention-qualification,free-quote-sql-qualification}.yml`: the cache key is now the exact pinned image reference, with restore and save split; the save only runs after a registry pull.

- `scripts/free-quote-platform-sources.mjs` (+ node test): exposes the pinned auth/storage images for the cache key.
