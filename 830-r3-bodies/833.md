## Linear issue ID
- Issue: [OVD-901](https://linear.app/overdrafter/issue/OVD-901) (child of OVD-840, follow-up to #802 / OVD-843). This is the main PR for the issue.

## Summary
verify.yml runs verify-overdrafter on every PR in report mode, and provider/fixture judged **FAIL** at main. The cause was the feature map, not the app: the map ran `e2e/journeys/jarvis-front-door.spec.ts`, whose main journey is `test.fail()` until OVD-805, and the judge correctly fails expected-failure journeys.

- `feature-specs.mjs`: `jarvis-front-door` moves out of `FEATURE_SPECS` into a new `PENDING_SPECS` list. Each entry names the unblocking issue (OVD-805) and a reason. A pending spec is not run and never counts as a pass. The CLI logs it on **stderr** as `PENDING: ...`, so `verify.sh` doesn't need to change and its stdout parsing is untouched.
- `admin-operations.spec.ts` stays mapped to `e2e/admin-operations.config.ts`. #802 already pointed it there, and its `baseURL` skip doesn't fire under that config: 6/6 pass locally, with 0 skipped. The existing `skipMismatches` test guards it, and a new test asserts it stays on that config.
- `verify-result-judge.mjs`: lists pending specs in `verify-result.json` (`pendingSpecs`) and in the summary under "Pending (not run, not counted as passing)". **The verdict logic is unchanged.**

## Gates not loosened
- No threshold was removed, and no workflow file changed. `verify.sh` and `verdict.mjs` are unchanged.
- Any skipped, flaky, failed, timed-out or `test.fail()` journey that runs still gives FAIL. A new judge test proves that a pending spec's `test.fail()` journey still FAILs if it runs anyway.
- New static checks:
  - No mapped spec may contain `test.fail(` or `test.fixme(`.
  - Every pending entry must name an `OVD-<n>` issue, its spec must exist and must not also be mapped, and the spec must still carry a top-level `test.fail(...)` that names that issue.

  So when OVD-805 lands and the `test.fail()` is removed, the skill test goes red until the spec moves back into `FEATURE_SPECS`. I checked both checks by mutation: re-adding the spec to the map turns 3 tests red, and swapping `test.fail` for `test.skip` turns the pending test red.
