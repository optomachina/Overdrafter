## OVD-880: staging guard requires TLS and refuses libpq overrides

This PR is based on main, which already includes #811 (OVD-839).

- The URL must now end in `?sslmode=require` or `?sslmode=verify-full`. A missing sslmode, `disable`/`allow`/`prefer`/`verify-ca`, `options=` and any other parameter are all refused.
- On top of the existing six, the guard now also refuses `PGSSLMODE`, `PGOPTIONS`, `PGSSLROOTCERT` and `PGTARGETSESSIONATTRS` when set (even to an empty string), so 10 env vars in total.
- Pooler host: the guard now allows only `aws-0-us-west-1.pooler.supabase.com` and refuses `aws-1-us-west-1`. A credential-free TLS startup probe as `postgres.ldmambwtksfvqdufhaam` (posted on OVD-880) got a SASL auth request from `aws-0` (the tenant exists there) and "tenant/user not found" from `aws-1`; `scripts/seed-staging.test.mjs` already uses `aws-0` for staging, and `aws-1` is the host the prod-only ovd373 access tool uses. A test pins that `aws-1` with the staging tenant user is refused. This PR's code and tests make no database connection; the orchestrator's separate unauthenticated startup probe established the host. Blaine can confirm the host read-only in the staging dashboard's Connect panel; the code and runbook note this.
- Tests: each new env var is refused through the function and through `main`. Missing and weak sslmode are refused, and `options=` is refused alone, before sslmode and after it. `require` and `verify-full` are accepted on both the direct and pooler hosts. Each extra-parameter fixture (`service`, `host`, `hostaddr`, `target_session_attrs`, `application_name`) is built on a URL that already ends in `?sslmode=require`, on both hosts, and the test first asserts that base URL is accepted, so each fixture is refused only for its own parameter.
- The runbook (`docs/runbooks/staging.md`) is updated to match.

This PR's code and tests make no database connections; no dependency or workflow changes.
