Build model: **opus** (source: the Release design comment on OVD-878).

## What
- **Role attributes and grants:** in CREATE/ALTER ROLE or USER (and CREATE GROUP), `superuser`, `createrole` and `replication` are flagged (class auth). `bypassrls` was already flagged by OVD-866. The `no*` forms only produce informational hits, except `nobypassrls`, which an OVD-866 rule keeps sensitive. Membership in `postgres`, `supabase_admin`, `service_role` or `authenticator` is flagged when granted by `GRANT … TO`, `CREATE ROLE/USER/GROUP … IN ROLE/IN GROUP` or `ALTER GROUP … ADD USER`. The word `role`/`roles` in the argument of `EXECUTE` or `format()` is flagged (`auth_dynamic_role(s)`) and can never be exempted.
- **Exemptions, `supabase/tests/**` only (gate_loosening):** each one is in the rule table with a reason, each must carry `gate_loosening: true`, and every hit it clears is listed under `gate_loosening` and in the job summary.
  - `tests_set_role_unprivileged`: a top-level statement that is exactly `SET [LOCAL] ROLE anon|authenticated` (unquoted, comments stripped, optional `;`).
  - `tests_reset_role` (new this round): a top-level statement that is exactly `RESET ROLE` (optional `;`). RESET ROLE only goes back to the session role the test connected as, so it can't escalate. `RESET ROLE` outside `supabase/tests/**`, quoted (`reset "role"`), or built in a DO block or EXECUTE string is still sensitive.
  - Everything else stays sensitive: privileged targets, quoted targets, trailing tokens, `set_config('role', …)`, switches inside strings or DO bodies, and every path outside `supabase/tests/**`.
- **Tokenizer matches Postgres (final round):**
  - A `--` comment now ends at LF **or CR**, so CRLF works and a lone CR ends the comment too, as in Postgres (`non_newline [^\n\r]`). The statement splitter uses the same loop, so it agrees.
  - Identifiers and dollar-quote tags work as in the Postgres scanner (`scan.l` ident_start/ident_cont, dolq_start/dolq_cont): **every code point at or above U+0080** is an identifier and dollar-tag character. So `aé$$` and `a—$$` are one identifier, `$é$…$é$`, `$—$…$—$` and `$😀$…$😀$` are dollar strings, and `ée'…'` is not an `E''` string. NBSP, emoji and BOM are identifier characters now. `set role anon<NBSP>;` stays sensitive because Postgres reads `anon<NBSP>` as a single word.
  - **Fail closed on unknown characters:** this only fires for an unexpected ASCII control character (U+0000–U+0008, U+000E–U+001F, U+007F) at any string depth. That file gets **no exemptions**. The rules run over the parsed tokens and also over a raw reading that treats comments and quotes as code, and every hit from either is sensitive. The reason `sql:tokenizer_unknown_char: U+XXXX on line N …` is added, and the file also gets **every class a SQL rule can add (`rls`, `definer`, `auth`)**, even if no rule hit. Characters inside comments and quoted identifiers don't trigger this.
- **Hit details:** each hit reports its rule id, path and line (`sql_hits`).

## Known limits (unchanged)
- A role switch spelled from fragments that never contain the word role (`execute 'set ' || 'ro' || 'le anon'`) isn't detected.
- Line numbers count LF only, so a file that uses lone CRs reports shifted lines. This affects the report only, not detection.
