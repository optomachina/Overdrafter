## Summary

The `land` skill now handles `main`'s strict branch protection. Today Release merges every PR by hand under strict. This adds `.codex/skills/land/land_strict_merge.sh <pr>`, which SKILL.md step 8 runs and step 9 routes on by exit code:

1. Read the PR in one `gh` call and pin `headRefOid`.
2. If the pinned head does not contain a freshly fetched `origin/main` (`git fetch --quiet --no-tags -- origin ...` plus `git merge-base --is-ancestor`), update it with `PUT repos/{owner}/{repo}/pulls/<n>/update-branch` with `expected_head_sha=<pin>`. That API always merges and has no rebase mode, and GitHub refuses it if the head moved. No rebase, no force push.
3. Wait (bounded) for the new head. Prove it is exactly that update merge: two parents, the first is the old pin and the second is already on `origin/main`. Only then re-pin.
4. Wait (bounded) for `ci` and `provider-go-live` on the pin, read from `commits/<pin>/check-runs`. Only GitHub Actions (app 15368) runs whose `head_sha` and `name` match count. No runs yet means pending, never failed. Any completed non-success (failure, cancelled, neutral, skipped, timed_out, stale, null, empty) means failed. Every poll re-reads the PR and stops if the head changed.
5. Re-read state, draft, base, head and `mergeStateStatus` right before merging. CLEAN, HAS_HOOKS or UNSTABLE: merge. BLOCKED or UNKNOWN: wait. BEHIND: re-check with git, and if `main` really moved, run another update round (at most 3). DIRTY: conflict. Anything else: stop.
6. Run `gh pr merge <n> --squash --match-head-commit <pin>`. Then report success only on MERGED with `headRefOid == pin` and a 40-hex `mergeCommit.oid`. A failed merge command is verified against the same pin and is never re-read and re-pinned.

Exit codes: 0 merged and verified; 2 precondition; 3 required check failed (Rework); 4 timeout; 5 head, SHA, history or state mismatch, or merge not verified (Human Review); 6 conflict (Rework); 7 update cap.

## Problem

Under strict mode, a PR that falls behind `main` cannot merge. The old skill (a bare `gh pr merge --squash --delete-branch` or `--auto`, plus a 20-minute state poll) could not bring a PR current, so every landing fell back to Release doing it by hand. #828's two repair rounds on this file kept finding shell edge cases, so the file was left unchanged there.

## Acceptance criteria addressed

- [x] Behind `main`: the branch is updated with the GitHub update-branch API as a merge, never a rebase or force push (the REST API has no rebase mode; `expected_head_sha` is sent).
- [x] The new head SHA is waited for and re-verified: 40-hex, two parents, first parent = old pin, second parent on `origin/main`.
- [x] `ci` and `provider-go-live` are re-verified as passed on that new head (SHA-bound check-runs API, app 15368 only).
- [x] The merge is `gh pr merge --match-head-commit <sha>`.
- [x] Fails closed on any mismatch, timeout or unknown state (bounded polls, enum allow-lists, distinct exit codes).
- [x] #828 review edge cases are handled explicitly:
  - quoting: every expansion is quoted, there is no `eval`, and the tests run from a temp path that contains a space;
  - SHA validation is whole-string, `case "$x" in *[!0-9a-f]*)` plus `${#x} -eq 40` under `LC_ALL=C`, with no grep. A jq sentinel keeps trailing newlines, so `<sha>\n` stays malformed, and NUL bytes are mapped to `!` inside jq, because bash would silently drop them;
  - `git fetch --quiet --no-tags -- origin ...`;
  - polling timeouts are bounded counts for the head, checks, mergeability and merge confirmation, all configurable and validated. Each `gh` call runs under `timeout` (60 s) when coreutils `timeout` is installed; `git fetch` calls are not individually time-limited;
  - a head change between steps is caught at every poll and before merge, and `expected_head_sha` covers the update itself;
  - after an update, checks not yet registered count as pending, not as a failure or Rework (#828 Sonnet blocker @ 1b86a50e);
  - a retry cannot re-pin a merged head (#828 Codex blocker 2 @ 8d71dba5);
  - a stale BEHIND right after an update does not trigger a second update (#828 non-blocking).
- [x] `land_watch.py` treats QUEUED and IN_PROGRESS runs, null or empty conclusions, PENDING or EXPECTED status contexts, and an empty rollup as waiting (OVD-889 bullet 4).

## Rollback / risk notes

- Not exercised against live GitHub. Everything above runs against a stub `gh`. The REST update-branch call with `expected_head_sha`, check-runs `filter=latest` and `--match-head-commit` follow GitHub's documented behaviour, but the first real landing should be watched.
- `{owner}/{repo}` placeholders resolve from the checkout's gh default repo. A checkout with an ambiguous remote fails closed (exit 5).
- Required checks are hardcoded as `ci provider-go-live` from app 15368 (overridable by env). If branch protection changes, update `LAND_REQUIRED_CHECKS`/`LAND_REQUIRED_APP_ID` defaults.
- An update round creates a merge commit on the PR branch. That is the intended strict-mode behaviour, and it resets checks.
- Rollback: `git revert` the squash commit. Landing falls back to the manual procedure kept in `docs/runbooks/merge-queue.md`.
