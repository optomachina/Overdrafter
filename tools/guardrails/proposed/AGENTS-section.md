### Migration window

This section is new text. Blaine approves it, including the merge rule below, by committing it when he applies the guardrail.

Writes under `supabase/migrations/` and any hosted database change need Blaine's explicit yes for that change. Merge rule: the lead merges green PRs that passed independent review and QA and touch nothing on Blaine's hard list, workers never merge, agents never push to `main`, and a PR that changes anything under `supabase/migrations/` is merged only after Blaine's explicit yes. The `blaine-window` label is retired; it opens nothing and no guard reads it. To open a window Blaine writes the migration himself, or starts a local CLI session with `claude --setting-sources user,local`, which skips the project deny rules and hook for that session only. That flag works only in local CLI sessions; cloud and app sessions load the project settings regardless. `npm run qualify:ovd417` stays blocked for agents because it runs `supabase db push --db-url` against environment variable URLs the hook cannot see; Blaine runs it, or a local session started with `--setting-sources user,local` does. If `CLAUDE.md` still carries the PreToolUse hook paragraph from PR #664, Blaine removes it, because this section replaces it.

Claude Code enforcement is best effort. The primary block is the `permissions.deny` list in `.claude/settings.json`: `Edit(/supabase/migrations/**)` and `Edit(//**/supabase/migrations/**)` (which also cover Write and NotebookEdit, in the primary checkout and in worktrees), Edit on `.claude/hooks/**`, the `.claude` settings files, `tools/guardrails/apply.mjs` and `tools/guardrails/proposed/**`, the Bash rules for `supabase db push`, `npx supabase db push` and `npm run db:push`, `apply_migration` under every server name, and the other hosted Supabase write tools (branch, project and edge function operations) under every Supabase server name we know. Hosted `execute_sql` is not denied by name so read only queries keep working. `.claude/hooks/guard-migrations.mjs` backs this up on Bash, file edit and MCP calls. It runs with an absolute node path, NODE_OPTIONS and NODE_PATH cleared, and fails closed when it is missing or crashes. It blocks writes to `supabase/migrations/` and to the guard files (by redirect, tee, sed -i, cp, mv, rsync, install, git checkout or restore, or a copy whose source would land there, also when the file name inside that directory is generated), pipes into a shell, decoded or generated text run by an interpreter, shell scripts that do any of that (run by `bash`, `sh` or `source`, by path such as `./scripts/x.sh`, or as `-c` text), any run of `tools/guardrails/apply.mjs` (by path, also a generated or `~` path, through an interpreter, or through a package script), supabase CLI commands that create migration files or target a hosted project unless they are on a read only allow list (also through package.json scripts run by `npm`, `yarn`, `pnpm`, `bun`, `node --run`, `npx` or `npm exec`, workspaces included), `psql`, `pgbench` and other Postgres clients (in docker too) whose target is not provably loopback unless `psql` runs read only SQL, HTTP writes to Supabase APIs (each curl `--next` transfer checked on its own), `git push` to `main` (including `heads/main` and aliases given with `git -c`), the merges API and writes to the `main` ref, hosted Supabase write tools under any server name, and `execute_sql` unless it is a single read only statement. It blocks a merge or auto merge (MCP, `gh pr merge`, `gh api`, curl, or a GraphQL mutation) only when the PR's changed files include `supabase/migrations/`, and it fails closed when it cannot list them or resolve the PR. Reads pass, including `cat`, `sed -n`, `awk`, `jq`, `grep` and `head` with a redirect to a path that is not protected, `sort -o` to such a path, `eslint` and `prettier` without `--fix` or `--write`, `psql -f` against a loopback host, read only `sh -c` text, git reads after global options such as `-C` or through a `git -c alias` (a `!` alias is checked with its arguments appended), and `bash` with long options such as `--login` or `--noprofile` before `-c`. Local commands such as `supabase db reset`, `supabase migration repair --local`, `npm run db:reset` and `npm run e2e:prepare` pass. It never scans commit message, PR or review comment text, and text that only names a protected path is not a write. An agent holding a user token cannot be told apart from the user, so the real gates stay the deny rules, the no worker merge rule, and Blaine's yes. If a guard blocks you, stop and report; do not route around it.

Known residuals, one per line (each has a row in the hook's test file):
- A symlink made earlier hides its target.
- A path generated at run time (from file contents or a glob the hook does not expand) is not known.
- `git reset`, `stash`, `merge`, `pull` and `clean` move many files at once and are not inspected; `git push` of the current branch does not resolve a checked out `main`.
- A gh alias made before the guard is not expanded.
- `env -C` and `env --chdir` change directory without a `cd` the hook can follow.
- An interpreter script file (`node x.mjs`) is not inspected, and an interpreter given a protected path as an argument stays blocked; read the file with `cat`, `sed -n`, `head`, `grep` or `jq` instead.
- A script run by path whose `#!` line names an interpreter other than a shell (`#!/usr/bin/env node`, `python3`) is not inspected.
- Inline interpreter code (`node -e`, `python -c`) that builds a path by concatenation, or that calls `fetch` or `urllib`, is not resolved.
- A push refspec set with `git config remote.origin.push` is not read, so a later plain `git push` is not seen.
- A SQL function with side effects is not inspected by the `execute_sql` check: user defined ones, and Supabase shipped ones such as `realtime.send` and `pgsodium.create_key`.
- After a `cd` to a generated or unresolved directory, a script run by a relative path is read from the directory before that `cd`.
- A git `!` alias that places its arguments with `$1` or `"$@"` inside its text is not resolved, and a git alias that expands to another `-c` alias is expanded only once.
- A script that runs its own arguments (`"$@"`), such as `scripts/run-ovd373-locked-command.sh`, is not resolved, so the command it is given is not checked.
- `curl -K` reads options from a config file that is not inspected.
- Archive extraction (`tar -xf`, `unzip`) writes the paths stored in the archive, which are not read, so it can write into a protected directory.
- Plain text piped into an interpreter other than a shell (`echo ... | node`, `| python3`) is not inspected.
- A merge without a pinned head sha can race a push that adds a migration after the changed files were listed.
- The hook command carries the absolute node and checkout paths of the machine that ran `apply.mjs`; a session where those paths differ is blocked until `apply.mjs` is rerun there.
