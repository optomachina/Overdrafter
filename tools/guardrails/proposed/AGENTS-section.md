### Migration window

This section is new text. Blaine approves it, including the merge rule below, by committing it when he applies the guardrail.

Writes under `supabase/migrations/` and any hosted database change need Blaine's explicit yes for that change. Merge rule: the lead merges green PRs that passed independent review and QA and touch nothing on Blaine's hard list, workers never merge, and a PR that changes anything under `supabase/migrations/` is merged only after Blaine's explicit yes. The `blaine-window` label is retired; it opens nothing and no guard reads it. To open a window Blaine writes the migration himself, or starts a local CLI session with `claude --setting-sources user,local`, which skips the project deny rules and hook for that session only. That flag works only in local CLI sessions; cloud and app sessions load the project settings regardless. If `CLAUDE.md` still carries the PreToolUse hook paragraph from PR #664, Blaine removes it, because this section replaces it.

Claude Code enforcement is best effort. The primary block is the `permissions.deny` list in `.claude/settings.json`: `Edit(/supabase/migrations/**)` and `Edit(//**/supabase/migrations/**)` (which also cover Write and NotebookEdit, in the primary checkout and in worktrees), Edit on `.claude/hooks/**` and the `.claude` settings files, `apply_migration` under every server name, and the other hosted Supabase write tools (branch, project and edge function operations) under every Supabase server name we know. Hosted `execute_sql` is not denied by name so read only queries keep working. `.claude/hooks/guard-migrations.mjs` backs this up on Bash, file edit and MCP calls: it blocks writes to `supabase/migrations/` and to the guard files, pipes into a shell, decoded or generated text run by an interpreter, shell scripts that do any of that, supabase CLI commands that create migration files or change a hosted project (also through `npm`, `yarn` or `pnpm run`), `psql` and other Postgres clients against a host that is not local unless they run read only SQL, HTTP writes to Supabase APIs, hosted Supabase write tools under any server name, and `execute_sql` unless it is a single read only statement. It blocks a merge or auto merge (MCP, `gh pr merge`, or `gh api`) only when the PR's changed files include `supabase/migrations/`, and it fails closed when it cannot list them. Local commands such as `supabase db reset`, `npm run db:reset` and `npm run e2e:prepare` pass. It never scans commit message, PR or review comment text. Its known residuals are listed in its test file. An agent holding a user token cannot be told apart from the user, so the real gates stay the deny rules, the no worker merge rule, and Blaine's yes. If a guard blocks you, stop and report; do not route around it.
