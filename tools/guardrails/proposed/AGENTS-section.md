### Migration window

Writes under `supabase/migrations/` and any hosted database change need Blaine's explicit yes for that migration window. Agents never merge or apply migration PRs, and agents never apply the `blaine-window` label. To open a window Blaine writes the migration himself or starts the session with `claude --setting-sources user,local`, which skips the project deny rules and hook for that session only.

Claude Code enforcement is best effort. The primary block is the `permissions.deny` list in `.claude/settings.json`: `Edit(/supabase/migrations/**)` (which also covers Write and NotebookEdit) and every hosted Supabase write tool by name (apply_migration, execute_sql, branch and project operations, edge function deploys) under each server name we have seen, plus GitHub MCP merge. MCP rules cannot match arguments, so GitHub label writes cannot be denied narrowly; `.claude/hooks/guard-migrations.mjs` checks MCP label fields and paths instead, and blocks obvious Bash writes into `supabase/migrations/`, pipes into a shell, decoded or generated text run by an interpreter, and `supabase migration new|up` or `db push`. It never scans commit message text. Its known residuals are listed in its test file. An agent holding a user token cannot be told apart from the user, so the real gates stay the deny rules, the no merge rule, and Blaine's yes. If a guard blocks you, stop and report; do not route around it.
