## Implementation and trust boundaries

The entrypoint is `scripts/run-ovd419-job-diagnostic.mjs`. Importing it performs
no cloud operation. Its explicit execution form requires a private packet file,
a private reference to an actual user approval message, and a new private
evidence path. None of those operational files is generated by these sources
or by the offline implementation task. A source commit is not runtime authority.

The bootstrap imports Node builtins only. Before application/helper imports it
checks a direct user message in this task's owned local Codex session transcript,
the exact packet digest and approval sentence, source/artifact hashes, and entire
script/dependency/SDK/Python trees. The transcript reference is a locator and
byte-prefix hash; caller-supplied role, text, timestamps or approval booleans are
not authoritative. A later user message invalidates that approval for further
mutation. Assistant, tool, delegated text, other-task messages, generic approval,
modified prefixes and expired windows reject. This uses the user's local Codex
transcript and OS account as the trust boundary; it is not a cryptographic
human-identity service or protection from a hostile process with the same user
privileges. Independent verification of the exact launcher remains mandatory.

`ovd419-job-diagnostic.mjs` is the injected state machine and strict packet
validator. The action is pinned to the original proposal, exact existing
project/region/Job/Service/owner, qualified candidate image, baseline image and
baseline Service build. All configuration, snapshot, account, secret-version,
inventory, control and egress bindings are explicit future inputs. Only the Job
is mutable. Dispatch is attempted once even if its response is lost. An
independent complete inventory can attribute the single added execution; missing
or conflicting attribution does not trigger a retry.

`ovd419-diagnostic-adapter.mjs` uses the existing supported Job replacement and
Job execution argument/environment override paths. It never sends a Service
mutation command. Replacements preserve the captured baseline Job spec and carry
the current resource version. The candidate differs only by image; restoration
reinstates the captured spec. Resource, snapshot, controls, execution inventory,
permissions, account and Service identity are re-observed before mutation.
The existing stable-egress and operational-envelope evaluators are reused.
Intermediate checks permit only the explicitly modeled image mismatch and
pending NAT/execution states; final checks require baseline parity and quiescence.

`ovd419-diagnostic-runtime.mjs` is a separate, literal runtime module. It is read
as bytes and hash-checked, never imported on the controller. It preserves the
previous in-Job snapshot/UID/generation/configuration/inventory pre-network guard,
adds packet/expiry checks, and emits only the fixed successful classification.
Unsuccessful classifications retain PR #494's fixed `probeReason` marker.
The source worker/image has not changed. The result reader rejects duplicate,
saturated, contradictory, unknown, or incorrectly attributed log evidence and
projects fixed fields before persistence.

`ovd419-diagnostic-bindings.mjs` verifies complete local artifact trees and the
qualified build attestation, rechecks the clean local commit, and provides the
durable admission mechanics. Production uses the same owner-lock location as
the existing release runner, so competing old/new controllers reject. A new
diagnostic consumption store is keyed by the bound direct-approval transcript
prefix and packet. Atomic exclusive creation plus synchronization rejects replay
across instances/processes. Existing locks or partial owner state are never
cleared automatically. Tests use only `ovd419-TEST-ONLY-*` locations and
`TEST-ONLY-NOT-AUTHORITY` records. No live owner or authority was created in tests.

## Finite failure and evidence

The packet's CPU/memory bounds select only supported explicit values; its server
task timeout is at most 900 seconds and its client execution deadline must cover
that timeout without exceeding 15 minutes. A read is at most 30 seconds, a
mutation at most 10 minutes, initial preflight at most 5 minutes, and recovery at
most 50 minutes 35 seconds. The recovery allowance includes restoration and the
historical 40-minute-35-second NAT observation envelope. Poll intervals and a
maximum of 10,000 total command/database reads are explicit, bounded inputs;
choose a sufficient reviewed budget for the selected complete observation path.
These are ceilings, not defaults or verified dollar estimates. No extra task,
automatic retry, new infrastructure, purchase, quote or order is implemented.

After a mutation attempt the controller attempts baseline restoration on both
authenticated and unsuccessful outcomes when independent observations show it
is safe. Expiry or user interruption cannot authorize another dispatch, but the
approved automatic restoration envelope remains available. Unsettled timed-out
capabilities, active/ambiguous executions, resource/owner/source drift, failed
restoration, exhausted bounds or unproved containment retain the owner sentinel;
the code does not race an outstanding request or silently overwrite drift.

Evidence is bounded JSONL: the classification/containment record is synchronized
with `evidenceStage: before_owner_release`, followed by a separately synchronized
owner-disposition record. Failed first-record persistence prevents release.
Failure to append the disposition returns `owner_receipt_unwritten`; the first
record remains historical evidence and cannot prove owner release. Successful diagnostic evidence means one fixed
classification captured **and** baseline containment verified; `authenticated`
is reported separately. Unknown/no result remains `inconclusive`.
`releaseQualified` and `retryAuthorized` are always false. Raw cloud/provider
logs, credentials, cookies, URLs, DOM, files and snapshot contents are omitted.
