## Failure contracts and repairs

1. A stale task previously became failed only in work_queue. Its queued/running
   result retained the free reservation indefinitely. A separate service-only
   RPC now scans reserved admissions after every reaper pass, even when the pass
   reaped zero new tasks. This covers a crash between the queue commit and RPC.
2. Deleting an archived reserved job previously removed the canonical request
   while retaining an unresolvable bare-ID receipt. A private BEFORE DELETE
   trigger refuses deletion until the free admission is terminal. It neither
   deletes evidence nor guesses an outcome.
3. Pending/unknown confirmation controls previously erased the safe replay
   reference. The separately committed UI fix locks those controls and retains
   the exact scope/reference while the outcome is unresolved.

## Lock graph and authority

The queue update commits before reconciliation. There is no queue-status trigger
that locks a request or result. A candidate is resolved from its immutable permit,
not work_queue payload IDs. The RPC takes result -> request -> queue locks with
SKIP LOCKED, re-reads its receipt, validates every pinned identity with null-safe
comparisons, and calls the existing finalizer (request -> receipt). Busy rows are
deferred and revisited when the bounded admission-ID cursor wraps. The RPC
requires READ COMMITTED. Missing/corrupt bindings retain capacity and produce an
indeterminate count; the worker reports that condition and still advances its
cursor so an invalid row cannot starve later pages.

Only failed/cancelled tasks with cleared worker/claim timestamps qualify. A
reclaimed/retried running task is deferred. A queued/running result is failed only
when the request is still active. Existing canceled-request handling is reused;
canonical success is never overwritten. A later stale result write is rejected
by the existing released-receipt fence. Policy disablement does not suppress
terminal accounting.

The delete trigger is explicitly VOLATILE and obtains no request/result/receipt
row locks. Preserve the existing admission invariant: its unconditional jobs
UPDATE (20260812044000 migration, before admission insertion) serializes deletion.
At READ COMMITTED, the trigger's fresh query observes a committed admission after
waiting for the job lock; at REPEATABLE READ/SERIALIZABLE the older delete snapshot
must receive serialization failure after that concurrent row update. Do not rely
on a foreign-key key-share lock alone. This reasoning still needs observed races.

The RPC revokes PUBLIC/anon/authenticated execution and grants only service_role.
The private trigger helper has no direct client/service execution grant. Search
paths are pinned to pg_catalog. There are no table grants or RLS changes.

## Authored deterministic coverage

`scripts/qualification/free-quote-terminal-lifecycle.sql` is a rollback-only
pgTAP specification, not a result. It checks actual role invocation, bounded
inputs, queue-only crash recovery, repeated sweeps, queued/running/uncleared-lease
preservation, late-success fencing, success before cleanup failure, cancellation,
exact cost retention, reserved/consumed/released deletion, and forged/null task or
lane bindings. Worker unit tests check the RPC call after a zero-row sweep, commit
ordering, cursor wrap, retry after RPC failure, malformed responses, diagnostics,
and per-call deadlines. Unit mocks do not establish SQL behavior.

Required two-session qualification on the final migration:

- Canonical success locks first: sweeper defers, then preserves one consumed receipt
- Sweeper settles first: late canonical write fails fenced, one released receipt remains
- Cancellation locks request first: sweeper defers without queue/result deadlock
- Sweeper locks first: cancellation observes terminal request after commit
- A task is requeued/reclaimed between scan and lock: fresh status/lease prevents release
- Admission owns job first: delete waits then rejects reserved at READ COMMITTED
- Delete owns job first: concurrent admission cannot commit a dangling receipt
- Repeat both delete orders at REPEATABLE READ and SERIALIZABLE; record 40001 where required
- Concurrent sweepers, multiple pages, locked first-page rows, corrupted bindings,
  interruption between queue commit/RPC, and exact retry after ambiguous RPC response
- Force constraints immediate/deferred; preserve all spend rows and historical receipts

Record actual waits, lock graph, SQLSTATE, final row state, and zero unexpected
capacity debit. A timeout, skipped row, or authored assertion is not a pass.
