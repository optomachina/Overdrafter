## Composition of the two dispatch wrappers

Both drafts move `public.api_authorize_provider_worker_dispatch` and `public.api_authorize_xometry_beta_worker_dispatch` into `private` and install a public wrapper with the same signature. `ALTER FUNCTION ... RENAME` and `SET SCHEMA` keep the OID, body, `proconfig` and ACL, so whichever draft runs second wraps the first one's wrapper.

722 then 723 (traced from `ovd-722.sql:420-507` and `ovd-723.sql:1068-1162`):

* generic: public (723 export gate) -> `private.provider_worker_dispatch_core` (the 722 wrapper: kill switch) -> `private.api_authorize_provider_worker_dispatch_pre_ovd722` (original body).
* Xometry: public (723) -> `private.xometry_beta_worker_dispatch_core` (722 wrapper) -> `private.api_authorize_xometry_beta_worker_dispatch_pre_ovd722` (original).

723 then 722:

* generic: public (722 kill switch) -> `private.api_authorize_provider_worker_dispatch_pre_ovd722` (the 723 wrapper) -> `private.provider_worker_dispatch_core` (original).
* Xometry: public (722) -> `private.api_authorize_xometry_beta_worker_dispatch_pre_ovd722` (723 wrapper) -> `private.xometry_beta_worker_dispatch_core` (original).

In both orders both gates stay in the call chain. Name collisions do not happen, each script revokes the moved function and grants only `service_role` on the new public one, and the generic wrapper's Xometry branch always resolves `public.api_authorize_xometry_beta_worker_dispatch` at run time. No wrapper is lost on apply. The problems are on rollback, in test pins, and in which denial wins (RX-1, RX-2).

## Findings

### Blocker

**R723-1. PHASE 1 is not expand only. It turns off dispatch for every existing job, with no way to recover it short of a new upload.**
Evidence: `ovd-723.sql:57` labels PHASE 1 "EXPAND", but `:1068-1162` installs the dispatch gate and `:1166-1178` backfills a `missing` declaration for every job with files. `:981-1026` (`export_control_scan_denial`) denies any part whose drawing has no scan row, and no scan rows exist before the new worker runs. The only caller of `api_declare_job_export_status` is `uploadFilesToJob` (`src/features/quotes/api/uploads-api.ts:286`). `api_review_export_control_block` has no app caller.
Why it matters: as soon as PHASE 1 commits, every existing job is refused at both preflights (`export_declaration_missing`, then `export_scan_missing`). A customer can clear that only by uploading another file to the job. Clearing the scan denial also needs a new extraction. That is a product outage shipped in a step labeled expand. The notes (`ovd-723-notes.md:61-87`) accept it, but window 1 should not.
Fix: split PHASE 1. 1a (expand): tables, triggers, constants, `api_declare_job_export_status`, `api_get_job_export_control_status`, both `api_record_export_control_*` RPCs, the 1.13 upload move with the new overloads, and `current_user_has_export_cleared_upload`. 1b (enforce, a later window): the 1.16 wrappers and the 1.17 backfill. Ship 1b only after the worker has recorded scans for a while, after a declaration path exists for existing jobs that needs no upload, and after a plan to backfill scans or extract again is agreed.

### High

**R723-2. PHASE 1 breaks existing pgTAP suites on main, and the notes do not say so.**
Evidence: these suites assert `authorized = true` from a preflight, using fixtures that have no declaration and no scan: `main:supabase/tests/xometry_beta_dispatch_permits.sql:668-672`, `main:supabase/tests/free_confirmed_quote_access.sql:202`, `main:supabase/tests/provider_dispatch_preflight.sql:635`, `main:supabase/tests/provider_dispatch_preflight_concurrency.sql:306`. `main:supabase/tests/provider_dispatch_preflight.sql:40-49` also requires `proconfig` to contain `search_path=pg_catalog` for every `proname = 'api_authorize_provider_worker_dispatch'`. The 723 wrapper sets `search_path = ''` (`ovd-723.sql:1124`).
Why it matters: CI goes red the moment the draft is promoted, and none of these suites is in the companion list.
Fix: in the same PR, seed a `not_controlled` declaration and clean scan rows into those fixtures, and retarget the `proconfig` check to the private core (or pin the wrapper to `search_path = pg_catalog`, which is the repo convention for these RPCs).

**R722-1. The list of suites to retarget is incomplete. Two more suites on main fail after PHASE 2.**
Evidence: the header list is at `ovd-722.sql:13-21` and `ovd-722-notes.md:65-71`. Not listed: `main:supabase/tests/provider_dispatch_preflight.sql:40-49` (`proconfig` pin on `api_authorize_provider_worker_dispatch`, matched by `proname` in any schema) and `main:supabase/tests/provider_dispatch_permits.sql:175-186` (`search_path=pg_catalog` pin on `proname = 'api_request_provider_dispatch'`). The 722 wrappers use `set search_path = ''` (`ovd-722.sql:437,489,535,580`), and the renamed inner functions no longer match `proname`.
Why it matters: CI fails on promotion.
Fix: add both suites to the retarget list, or declare the four wrappers with `set search_path = pg_catalog` (they already qualify every reference), which keeps both pins passing unchanged.

**RX-1. Each rollback assumes it is the last migration applied, and does not check. Rolling back out of order silently removes the other PR's gate.**
Evidence: the 722 rollback (`ovd-722.sql:641-659`) runs `drop function public.api_authorize_xometry_beta_worker_dispatch(...)` and `drop function public.api_authorize_provider_worker_dispatch(...)`, then moves `private.*_pre_ovd722` back to `public`. The 723 R1 (`ovd-723.sql:1262-1271`) does the same with `*_core`.
Why it matters: with 722 then 723 applied, running only the 722 rollback drops the 723 wrapper and puts the original body back in `public`, so the export gate disappears without an error. The orphaned `private.*_core` functions then call `private.provider_kill_switch_engaged_text`, which the same rollback drops (`:666`). Without 723 applied, rolling back 723 drops the 722 wrapper in the same way. In LIFO order both rollbacks are correct.
Fix: start each rollback with a guard, for example `do $$ begin if pg_catalog.strpos((select prosrc from pg_proc where oid = 'public.api_authorize_provider_worker_dispatch(uuid,uuid,jsonb,text,timestamptz)'::regprocedure), 'provider_kill_switch_engaged') = 0 then raise exception 'not the outermost wrapper; roll back the later migration first'; end if; end $$;` (use the matching marker for 723). Record the required LIFO order in `docs/release/window-1/rollback`.

**R723-3. The 723 rollback cannot run as written. Followed literally, it leaves dispatch and upload unusable.**
Evidence: R2 is prose only (`ovd-723.sql:1254-1258`). R1 restores functions whose ACL was cleared earlier: `:699,:709` revoke the upload cores from `authenticated`, and `:1076,:1086` revoke the preflight cores from `service_role`. Rename and set schema keep that empty ACL, and the grants are restated only as comments (`:1272-1273,:1287`). `drop function public.current_user_has_export_cleared_upload(text)` (`:1288`) fails while the PHASE 2 storage policy still references the function, because policy expressions record a dependency in `pg_depend`.
Why it matters: an operator who runs only the SQL lines gets 42501 on every worker preflight and every browser upload. That still fails closed, but it is an outage during an incident.
Fix: write R2 and R1 as executable SQL. That means the full `job_files_storage_insert` policy from `main:supabase/migrations/20260815093000_enforce_founding_beta_file_boundaries.sql:383-398`, the exact `revoke`/`grant` pairs (`service_role` on both preflights, `authenticated` on both upload RPCs), and R2 before R1 inside one transaction. Add the RX-1 guard.

### Medium

**RX-2. The order of application changes which denial wins and which test pins hold.**
Evidence: with 722 then 723, the 723 export check runs first. The 722 pending suite then gets `export_declaration_missing` where it expects `provider_kill_switch_engaged` (`supabase/tests/pending/ovd722_provider_kill_switch.sql.pending:201-206,265-268`; task `...722101` has no job, and `ovd-723.sql:936-938` returns missing). With 723 then 722, the "byte for byte original body" claim at `ovd-722.sql:48-49` is false, because `*_pre_ovd722` holds the 723 wrapper, and each set of retargeted `prosrc` pins has to point somewhere else. On the worker side, a server kill switch denial becomes `cancelled_provider_disabled` (`worker/src/dispatchRouting.ts:115`), while an export denial becomes terminal manual follow up. So the order changes customer visible outcomes when both gates apply.
Fix: fix one order in the release manifest. Kill switch outermost is the better order (723 enforce first, 722 PHASE 2 second, or have the 723 wrapper call `private.provider_kill_switch_engaged` first when it exists). Write the retargets and both pending suites against that order.

**R723-4. Deploying worker or client code before PHASE 1 fails closed, but it stops more work than the notes describe.**
Evidence: the worker calls `api_record_export_control_clean_scan` inside drawing extraction (`worker/src/index.ts:577`), on the trusted reuse path (`:750`), and before every STEP quote (`:1264`). `recordExportControlCleanScan` throws on any RPC error, including PGRST202, 42883, 403 and transport errors (`worker/src/exportControl.ts:291-315`). The client's `declareCleanJobExportStatus` rethrows any RPC error (`uploads-api.ts:181`). `createJobsFromUploadFiles` creates the draft job before it declares (`uploads-api.ts:255,267,286`).
Why it matters: worker before migration means every extraction with a drawing fails, not only dispatch. Client before migration means every upload fails, after an empty draft job already exists. Both fail closed, which is correct, but each is an outage.
Fix: in the manifest, deploy PHASE 1a, then the worker, then the client. For hosted runs, consider a guard that checks the RPC once at worker startup and refuses readiness instead of failing each task. Declare before `createClientDraft`, or delete the draft when the declaration fails.

**R723-5. PHASE 2 takes an ACCESS EXCLUSIVE lock on `storage.objects`.**
Evidence: `ovd-723.sql:1229-1245` runs `drop policy` and then `create policy` on `storage.objects`.
Why it matters: both statements need ACCESS EXCLUSIVE. They queue behind any running storage query, and while they wait, every storage read and write in the project queues behind them.
Fix: ship PHASE 2 as its own short migration that starts with `set local lock_timeout = '3s';` and retry it on timeout. Apply it at low traffic, and not in window 1 (see the recommendation below).

### Low

**R722-2. Nested transaction control in a file the CLI runs as one unit.**
Evidence: `ovd-722.sql:54` `begin;` and `:610` `commit;`. There is precedent: 7 migrations on main do the same, for example `20261002133713_add_capability_preparation_retention.sql`.
Why it matters: if the runner already opened a transaction, the inner `begin` only warns, and the inner `commit` ends the runner's transaction early, so the migration history insert runs outside it. The script cannot be run twice: `create function` without `or replace`, and the renames, fail the second time.
Fix: drop both lines and let the runner own the transaction. Keep the `begin;`/`commit;` only around the commented rollback, which is run by hand.

**R722-3. The new private tables have no RLS, unlike the repo convention.**
Evidence: `ovd-722.sql:60-93` revokes all privileges but never enables RLS on `provider_kill_switches`, `provider_global_kill_switch` or `provider_kill_switch_audit`. On main, 26 private tables enable RLS and some force it (`main:supabase/tests/free_quote_job_meter.sql:12`). 723 enables RLS on its tables (`ovd-723.sql:188-191,570`).
Why it matters: there is no leak today, since `private` has no API usage and every grant is revoked. This is defense in depth only.
Fix: `alter table ... enable row level security; alter table ... force row level security;` on all three, with no policies. Access stays through the definer RPCs.

**R722-4. The sweep cannot use an index on its join, and it cancels tasks that have no vendor.**
Evidence: `ovd-722.sql:387` `where r.id::text = tasks.vendor_quote_result_id` cannot use the `vendor_quote_results` primary key. `:360` `provider_kill_switch_engaged_text(q.payload ->> 'vendor')` is true when `vendor` is null.
Why it matters: the sweep runs on every reaper interval (`worker/src/index.ts:1963`). A queued `run_vendor_quote` task with no `vendor` is cancelled as `cancelled_provider_disabled`, which is not the real reason (the handler would have failed it with "missing vendor").
Fix: join on `r.id = (tasks.vendor_quote_result_id)::uuid` behind a uuid regex check, and add `and q.payload ? 'vendor'` to `doomed`.

**R723-6. Several 723 RPCs leave `service_role` with EXECUTE.**
Evidence: `ovd-723.sql:430,480,685,859-880,914` revoke from `public, anon` only, so Supabase default privileges keep EXECUTE for `service_role`. 722 revokes `service_role` explicitly.
Why it matters: there is no exploit, because each body requires `auth.uid()` or a platform admin. Still, `has_function_privilege` audits will not match the 722 style.
Fix: add `service_role` to each revoke, except where the worker needs it.

**R723-7. `export_control_lookup_failed` turns transient errors into terminal denials.**
Evidence: `ovd-723.sql:972-973,1052-1053` use `exception when others`, which also catches 55P03 (lock not available), 57014 (statement timeout) and 40P01 (deadlock).
Why it matters: a lock timeout on the per job advisory lock (`:940`) sends the lane to manual follow up instead of a retry. It fails closed, but it adds noise.
Fix: raise again for SQLSTATE classes 40, 55 and 57 so the worker classifies them as `preflight_unavailable`, and keep `lookup_failed` for everything else.

**R723-8. Upload grants are cleaned up only on finalize.**
Evidence: `ovd-723.sql:794-804` inserts grants and `:848-851` deletes them on finalize. Nothing removes expired rows.
Fix: delete expired rows for the same `(organization_id, content_sha256, granted_to)` in prepare, or add a periodic cleanup.

**R723-9. The SQL gates in 723 fail closed.** `current_user_has_export_cleared_upload` returns false on any exception (`ovd-723.sql:909-910`). **RX-3. Lock behavior apart from R723-5.** Neither PHASE 1 locks a hot table. `ALTER FUNCTION ... RENAME/SET SCHEMA` and `CREATE FUNCTION` change only catalog rows. The 723 backfill is a single `insert ... select` over `jobs` and `job_files` with ACCESS SHARE locks. PostgREST needs a schema reload before the new 7 and 9 argument overloads resolve, and until then the new client fails closed (PGRST202).

**RX-4. Merging the two PRs conflicts.** `git merge-tree` reports conflicts in `worker/src/providerDispatchEnvelope.ts`, `worker/src/xometryDispatchPreflight.ts` and `worker/src/jev/operationalTask.test.ts`.
