# Registered result reader and internal runtime

Source only; no PostgreSQL, storage, Windows or native execution qualification is claimed.

`createNativeResultReader` loads the exact current task/attempt from private SQL, its frozen job/input snapshot, seven registered immutable object generations, and independently admitted process/filesystem context. Reads resolve registry Storage IDs internally and use the existing generation-aware private storage driver. The whole admission is reloaded and compared after all byte reads. Existing OVD561 SQL is the final locked authority check.

`createNativeResultRuntime` composes that reader with the seven-check verifier, exact-envelope durable persistence and existing finalization executor. `finalize` and explicit `replay` are internal owner operations. The default is disabled. Configuration supplies the already authorized owner SQL pool and receipt signing key directly. No environment lookup, credential setup or network call happens during composition. A private HTTP authentication/mount contract does not yet exist; this change deliberately adds no HTTP route.

## Additional migration purpose

`native-result-reader-forward.sql` adds one immutable owner-only attempt binding. Existing OVD575/576/577 evidence includes process identities and qualified stop provenance, but not independent input/candidate filesystem handle identities. Those cannot be learned from worker output reports.

The explicit owner admission writer takes independently captured filesystem identities and the SHA-256 of their retained qualification record. This is an owner attestation boundary, not automatic measurement or a claim that a hash establishes provenance. Only `postgres` may call the SQL writer; no public/service-role/worker grant is added. The operator must capture the two FILE_ID_INFO identities independently, bind the record to task, attempt, qualified evidence ID, host and both exact directory paths, retain its exact bytes, and calculate the digest. Never route worker filesystem JSON into this writer. A live independent capture integration is not supplied or qualified here.

The writer derives native and operation helper PID/start identities from existing independently validated and qualified journal launch roles, never caller process metadata. It requires READ COMMITTED: the SHARE locks wait for in-flight revocation and membership writers, and only a statement snapshot taken after the lock sees their commits, so REPEATABLE READ and SERIALIZABLE callers are refused before any authority read. It rejects missing/foreign qualification, stale/current-attempt loss, revoked admissions, absent qualified successful stop, aliasing filesystem handles and changed replay. An exact replay returns the immutable prior process binding. SQL and TypeScript validate filesystem shape and reuse existing strict Windows path rules.

## OVD-651 isolation race proof and window 2 apply order

`scripts/ovd651-isolation-race-proof.mjs` runs two real sessions against a disposable local PostgreSQL with narrow stub tables. It runs on PostgreSQL 17. It proves: the OVD-560 reverse retains a registration that commits while the reverse waits and refuses REPEATABLE READ; a registration that holds `storage.objects` FOR SHARE and then reads the registry completes while the reverse waits, and the reverse then refuses with the row and its binding retained, while a registry first control order deadlocks (40P01); the OVD-563 reverse refuses a stale REPEATABLE READ snapshot and a concurrently committed review; binding admission refuses REPEATABLE READ and, under READ COMMITTED, sees a revocation or membership removal that commits while it waits. Empty reverses and an unrevoked admission still succeed. `--source-rev <pre-fix sha>` reproduces the unsafe outcomes. Stubs do not qualify the canonical migrations.

Window 2 apply order (owner, READ COMMITTED, Blaine's yes required): staged OVD558, OVD560, OVD561 forward, `ovd561-pending-forward.sql`, `native-result-reader-forward.sql`, then OVD563. The caller of `load_native_pending_finalization(uuid,uuid)` and `persist_native_pending_finalization(uuid,uuid,text,text,text,uuid)` is `server/engineering/native-result-executor.ts`, already on main from #614; both functions are created only by `ovd561-pending-forward.sql` here. The real constraint is that `ovd561-pending-forward.sql` must be applied before any finalization runtime that uses main's executor is enabled. Later carves such as #620 (OVD-649) inherit that constraint through the executor; they do not add new calls to these functions. Rollback runs in reverse order on empty history only: OVD563 reverse, `native-result-reader-reverse.sql`, `ovd561-pending-reverse.sql`, OVD561, OVD560, OVD558. Every reverse refuses any isolation other than READ COMMITTED, then takes `pg_advisory_xact_lock(510, 2)` before any relation lock, so reverses run one at a time with each other and with the OVD558 reverse. The OVD560 reverse, like the OVD558 reverse, locks `storage.objects` before the registry. Stop the worker before any reverse: runtime finalization and native artifact mapping read the registry after `storage.objects`, and a reverse that drops a foreign key also locks the referenced tables, so a live worker can only make a reverse wait, time out or abort.

## Admission lock scope

Admission takes the attempt row FOR UPDATE, then SHARE locks revocations, operators, organization and project memberships and projects. It reads `public.engineering_workers`, `engineering_private.native_stop_admissions` and `public.engineering_task_execution` under READ COMMITTED after those waits but does not SHARE lock them. This is safe because the binding is not authority. Stop admissions are immutable history. The reader rechecks worker revocation and boot, the current attempt and the qualified stop on every load and again after all byte reads. OVD561 finalization then locks the worker and task execution rows FOR UPDATE and rechecks them before any mutation. A worker revocation or attempt change that commits just after admission therefore blocks finalization; it never lets a result through.

The attempt FOR UPDATE then SHARE lock order can deadlock with a writer that holds one of those tables and then wants the attempt row. PostgreSQL aborts one side. If admission is aborted, no binding is written. If the writer is aborted, its change never commits, so the admission read current state. Either way it fails closed.

The forward file runs with five second lock and thirty second statement timeouts. It refuses unless `current_user` is `postgres` (the effective role, not the table owner), these objects exist: the OVD575 observer evidence table and its two helper functions, the OVD576 stop qualifications table, the existing history mutation and actor access functions, the OVD560 registration function and the OVD561 finalization function, and the binding table is absent. It does not check any OVD577 object; the apply order covers OVD577.
