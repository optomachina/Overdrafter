# OVD-979 canonical lock order

This is the lock-order contract for the OVD-979 redesign that replaces draft #874. It sets one lock
order for every function that locks or writes the job, part, requirement,
extraction and queue tables. It adds a static check for that order and
records the remaining inversions. U2 changes lock acquisition and write order in
the approval/reset/reuse paths; approval policy remains unchanged.

## The order

| Level | Lock                                                                                          |
| ----- | --------------------------------------------------------------------------------------------- |
| L0    | Per-job advisory transaction lock (`ovd979:job:<id>`), only where a path needs request dedupe |
| L1    | `jobs` row, `FOR NO KEY UPDATE`                                                               |
| L2    | `parts` rows of the job, `ORDER BY id`                                                        |
| L3    | `approved_part_requirements`, `ORDER BY part_id`                                              |
| L4    | `drawing_extractions`, `ORDER BY part_id`                                                     |
| L5    | `work_queue` rows, `ORDER BY id`                                                              |

Rule: a transaction may skip levels. It never takes a lower level after a
higher one. Multi-row locks use a deterministic `ORDER BY`.

The check counts these as lock steps: advisory locks; `SELECT ... FOR
UPDATE/NO KEY UPDATE/SHARE/KEY SHARE`, attributed through `FROM`/`JOIN`
aliases (`FOR ... OF <alias>`) at the query level the clause belongs to, so a
lock inside a subquery counts against the subquery's table; `UPDATE`;
`DELETE`; `INSERT`, including `INSERT ... ON CONFLICT DO UPDATE`; and `LOCK
TABLE`. `FROM` lists are read in full: comma-separated items and every `JOIN`,
whether or not the table before it has an alias. Every call to another audited
function, including repeat calls in one statement, counts that function's locks
at the call site.

Tables outside L0–L5 that these functions lock on `main` (`job_files`,
`debug_extraction_runs`, `drawing_preview_assets`, `cad_preview_assets`,
`quote_requests`, `quote_runs`, `vendor_quote_results`, `vendor_quote_offers`,
`vendor_quote_artifacts`) are listed per function in `KNOWN_UNORDERED_LOCKS`.
Any other table outside the order is an error, and the list must match
exactly. Whether any of them joins the order is a Lead/Architect decision.

Two things differ from the plan written against #874:

- On `main`, `load_editable_project_part_context` takes no lock. The editable
  client paths therefore get no L1 from it; their first lock is their own
  first `UPDATE`.
- U5 uses `private.merge_pending_drawing_extraction`, a BEFORE trigger that
  modifies only `NEW`. It takes no additional row locks. The #874 trigger
  that updates a second active queue row is not installed.

## Enforcement

`scripts/check-lock-order.mjs` prints each audited function's sequence and
fails closed on any of these:

- the latest `CREATE` of an audited function can't be parsed. Its
  dollar-quoted body tag must appear inside its own `CREATE` statement, so a
  single-quoted or `BEGIN ATOMIC` body is an error, and it never falls back to
  an older definition or the next function's body. Headers inside comments
  are ignored;
- a lock on a table outside L0–L5 that isn't listed for that function in
  `KNOWN_UNORDERED_LOCKS`, or a listed one that no longer occurs;
- a `FOR ... OF <alias>`, a lock clause, or a `LOCK TABLE` target whose table
  can't be resolved;
- callee expansion reaching the depth cap of 3;
- any inversion pair not listed exactly for that function in
  `KNOWN_INVERSIONS`, or a listed pair that no longer occurs (each fixing PR
  removes its pairs);
- a call to a migration-defined function outside `AUDITED_FUNCTIONS` that
  isn't listed exactly for the caller in `KNOWN_UNAUDITED_CALLEES` (stale
  entries fail too), or a listed callee that directly locks an L0–L5 table;
- a key in any of the three known lists that isn't an audited function.

On `main`, the unaudited callees are permission checks, normalizers,
property-snapshot and seeding helpers, and audit-event writers
(`log_audit_event`, `append_commercial_admin_audit_event`). None of them
directly locks an L0–L5 table.

`scripts/check-lock-order.test.mjs` covers each of these and runs the check
against the repository in the normal Vitest suite, resolving paths from
`import.meta.url` so it doesn't depend on the working directory. It isn't wired
into a CI workflow.

Parsing is quote-aware: one scanner pass skips `'...'` strings (with `''`
escapes, and backslash escapes in `E'...'`), `"..."` identifiers and
`$$`/`$tag$` literals before it removes `--` and nested `/* */` comments, so
comment markers inside a literal can't hide a lock or a newer definition.

Unsupported statements fail closed (the check errors rather than skipping
them): `TRUNCATE`, `MERGE` (any action), `CALL` (procedures, which are never
expanded), and an `UPDATE`, `DELETE`, `INSERT`, `LOCK TABLE` or `FOR <lock>`
query on a table in a schema other than `public` or `private`. A function
defined outside `public`/`private` is recorded as unparsable, so an audited
function with that name, or a call to it from an audited function, is an
error. An unaudited callee that calls an audited function is an error, and
`KNOWN_UNORDERED_LOCKS` may not list an L0–L5 table. On `main` none of these
occur.

Limits: the check is static. It can't see dynamic SQL (`EXECUTE`), locks
taken by triggers, or locks inside an unaudited callee's own callees (only
the callee's direct statements are checked). The two-session dblink tests
(redesign PR 2 onward) cover real interleavings.

## Answers to the plan's open questions

1. The unaudited functions: `api_request_debug_extraction` inserts into
   `debug_extraction_runs` and `work_queue` (L5) and takes no other lock.
   `reset_job_after_manual_quote_cancellation` takes L1 only.
   `api_admin_complete_manual_quote_request` takes L0, then L1, then the
   quote/vendor-quote tables (outside the order), then L1 again; it touches no
   `parts` or `work_queue`.
2. Yes. `api_claim_next_task` uses `FOR UPDATE SKIP LOCKED`
   (`20260324120000_add_api_claim_next_task.sql`), so fix A in redesign PR 5
   works. Fix B stays recommended as a backup.
3. Yes (Architect). There is one canonical order: advisory, jobs, parts,
   requirements, extractions, work queue, with no per-path exceptions. In PR 2,
   `api_approve_job_requirements` takes the `jobs` lock at the top. U2 keeps
   its approval decisions and uses ordered write phases so the unchanged
   checker can verify every lock step, with two-session contention tests.
4. U5's final scope requires one active extraction **per part**, a stronger
   guard than the original proposed part/drawing pair. Its pre-index audit
   groups queued/running `extract_part` rows by non-null `part_id`, including
   missing, null and different drawing identities. A table write lock spans
   the audit and index creation. Duplicates abort the whole transaction;
   nothing is cleaned up automatically. A hosted read-only duplicate audit
   remains a separate release prerequisite; local proof does not satisfy it.

## U2 implementation and auxiliary-path audit

U2 is `20261030162500_ovd979u2_canonical_requirement_lock_order.sql`; its draft,
rollback hashes and local proof are documented in
[`migration-drafts/ovd-979u2-notes.md`](migration-drafts/ovd-979u2-notes.md).
The checker logic is unchanged. The three resolved functions' inversion entries
are removed. Writes use ordered phases because the checker counts subsequent
updates as locks even after a prelock. Reset reloads its permission-checked
context after the L1 wait; reuse rereads its target after locking the target job.

Auxiliary paths were reread from their latest migration definitions:

- `api_request_debug_extraction` (`20260317113000`) reads part/job, inserts a
  debug run and inserts L5 work. It never explicitly locks or writes L1–L4.
  The job/part foreign-key checks take KEY SHARE, compatible with U2's
  `FOR NO KEY UPDATE` on jobs. It needs no U2 SQL change.
- Manual cancellation's `private.reset_job_after_manual_quote_cancellation`
  trigger (`20260731015235`) updates only L1, conditionally on a manual request
  becoming canceled and a job awaiting manual review. It takes no parts,
  requirements or extraction lock. The enclosing `api_cancel_quote_request`
  (`20261002182714`) locks request/run rows outside L0–L5; updating the request
  fires that trigger before its queued vendor-task cancellation. Its general
  vendor-task branch also updates L5 and later L1. That general cancellation
  path is not made canonical by U2 and is not one of the audited functions.
- `api_admin_complete_manual_quote_request` (`20260731015300`) takes two L0
  advisory locks, locks L1, then request/run and vendor-quote rows, and updates
  L1 again. The part lookup is a plain read; it never locks L2–L5. It needs no
  U2 SQL change. Its existing `FOR UPDATE` job strength is unchanged.

The quote-table locks are outside the defined levels. This audit does not claim
that cancellation versus completion has a single global order across those
unordered tables: cancellation locks the request before its trigger can lock
the job, whereas completion locks the job before the request. That existing
quote-lifecycle concern requires its own scoped review, not a silent expansion
of this approval-lock unit.

`supabase/tests/ovd979u2_lock_order.sql` observes real `pg_locks` waits and
blocking PIDs for all four requested pairs, in both transaction directions,
with `lock_timeout` set. Additional L1-holder probes fail against the prior
bodies. U5 resolves the request-path inversion. These tests remain evidence for
the exercised interleavings, not blanket deadlock freedom across unaudited paths.
