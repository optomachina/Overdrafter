# OVD-979 canonical lock order

This is PR 1 of the OVD-979 redesign that replaces draft #874. It sets one lock
order for every function that locks or writes the job, part, requirement,
extraction and queue tables. It adds a static check for that order and
records where `main` breaks it today. It changes no SQL behavior.

## The order

| Level | Lock                                                                                          |
| ----- | --------------------------------------------------------------------------------------------- |
| L0    | Per-job advisory transaction lock (`ovd979:job:<id>`), only where a path needs request dedupe |
| L1    | `jobs` row, `FOR NO KEY UPDATE`                                                               |
| L2    | `parts` rows of the job, `ORDER BY id`                                                        |
| L3    | `approved_part_requirements`, `ORDER BY part_id`                                              |
| L4    | `drawing_extractions`, `ORDER BY part_id`                                                     |
| L5    | `work_queue` rows, `ORDER BY id`                                                              |

Rule: a transaction may skip levels. It never takes a lower level after a
higher one. Multi-row locks use a deterministic `ORDER BY`.

The check counts these as lock steps: advisory locks; `SELECT ... FOR
UPDATE/NO KEY UPDATE/SHARE/KEY SHARE`, attributed through `FROM`/`JOIN`
aliases (`FOR ... OF <alias>`) at the query level the clause belongs to, so a
lock inside a subquery counts against the subquery's table; `UPDATE`;
`DELETE`; `INSERT`, including `INSERT ... ON CONFLICT DO UPDATE`; and `LOCK
TABLE`. `FROM` lists are read in full: comma-separated items and every `JOIN`,
whether or not the table before it has an alias. Every call to another audited
function, including repeat calls in one statement, counts that function's locks
at the call site.

Tables outside L0–L5 that these functions lock on `main` (`job_files`,

exactly. Whether any of them joins the order is a Lead/Architect decision.

- On `main`, `load_editable_project_part_context` takes no lock. The editable
  client paths therefore get no L1 from it; their first lock is their own
  first `UPDATE`.
- The `private.release_deferred_drawing_extractions` trigger exists only in
  #874, so it isn't audited here.

## Enforcement

`scripts/check-lock-order.mjs` prints each audited function's sequence and
fails closed on any of these:

- the latest `CREATE` of an audited function can't be parsed. Its
  dollar-quoted body tag must appear inside its own `CREATE` statement, so a
  single-quoted or `BEGIN ATOMIC` body is an error, and it never falls back to
  an older definition or the next function's body. Headers inside comments
  are ignored;
- a lock on a table outside L0–L5 that isn't listed for that function in
  `KNOWN_UNORDERED_LOCKS`, or a listed one that no longer occurs;
- a `FOR ... OF <alias>`, a lock clause, or a `LOCK TABLE` target whose table
  can't be resolved;
- callee expansion reaching the depth cap of 3;
- any inversion pair not listed exactly for that function in
  `KNOWN_INVERSIONS`, or a listed pair that no longer occurs (each fixing PR
  removes its pairs);
- a call to a migration-defined function outside `AUDITED_FUNCTIONS` that
  isn't listed exactly for the caller in `KNOWN_UNAUDITED_CALLEES` (stale
  entries fail too), or a listed callee that directly locks an L0–L5 table;
- a key in any of the three known lists that isn't an audited function.

On `main`, the unaudited callees are permission checks, normalizers,
property-snapshot and seeding helpers, and audit-event writers
(`log_audit_event`, `append_commercial_admin_audit_event`). None of them
directly locks an L0–L5 table.

`scripts/check-lock-order.test.mjs` covers each of these and runs the check
against the repository in the normal Vitest suite, resolving paths from
`import.meta.url` so it doesn't depend on the working directory. It isn't wired
into a CI workflow.

Limits: the check is static. It can't see dynamic SQL (`EXECUTE`), locks
taken by triggers, or locks inside an unaudited callee's own callees (only
the callee's direct statements are checked). The two-session dblink tests
(redesign PR 2 onward) cover real interleavings.

## Answers to the plan's open questions

1. The unaudited functions: `api_request_debug_extraction` inserts into
   `debug_extraction_runs` and `work_queue` (L5) and takes no other lock.
   `reset_job_after_manual_quote_cancellation` takes L1 only.
   `api_admin_complete_manual_quote_request` takes L0, then L1, then the
   quote/vendor-quote tables (outside the order), then L1 again; it touches no
   `parts` or `work_queue`.
2. Yes. `api_claim_next_task` uses `FOR UPDATE SKIP LOCKED`
   (`20260324120000_add_api_claim_next_task.sql`), so fix A in redesign PR 5
   works. Fix B stays recommended as a backup.
3. Yes (Architect). There is one canonical order: advisory, jobs, parts,
   requirements, extractions, work queue, with no per-path exceptions. In PR 2,
   `api_approve_job_requirements` takes the `jobs` lock at the top and keeps
   the rest of its body unchanged, with two-session tests that run the
   sessions against each other.
4. Yes (Architect). First run a read-only duplicate audit: queued or running
   `extract_part` rows in `work_queue`, grouped by `part_id` and
   `payload->>'drawingFileId'`, with `count > 1`. PR 5's migration repeats that
   check in a `DO` block that runs before the migration creates its partial
   unique index on queued/running `extract_part` rows, and aborts the
   migration if any duplicates exist, so the index is never attempted over
   duplicates. There is no automatic cleanup. Rows with a null
   `drawingFileId` are handled explicitly.
