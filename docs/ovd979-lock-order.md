# OVD-979 canonical lock order

This is PR 1 of the OVD-979 redesign that replaces draft #874. It sets one lock
order for every function that locks or writes the job, part, requirement,
extraction and queue tables. It adds a static check for that order and
records where `main` breaks it today. It changes no SQL behavior.

## The order

| Level | Lock                                                                                          |
| ----- | --------------------------------------------------------------------------------------------- |
| L0    | Per-job advisory transaction lock (`ovd979:job:<id>`), only where a path needs request dedupe |
| L1    | `jobs` row, `FOR NO KEY UPDATE`                                                               |
| L2    | `parts` rows of the job, `ORDER BY id`                                                        |
| L3    | `approved_part_requirements`, `ORDER BY part_id`                                              |
| L4    | `drawing_extractions`, `ORDER BY part_id`                                                     |
| L5    | `work_queue` rows, `ORDER BY id`                                                              |

Rule: a transaction may skip levels. It never takes a lower level after a
higher one. Multi-row locks use a deterministic `ORDER BY`.

An `UPDATE` or `DELETE` locks every row it touches, so the check counts it
like `FOR UPDATE`. A call to another audited function counts that function's
locks at the call site.

- On `main`, `load_editable_project_part_context` takes no lock. The editable

  first `UPDATE`.
- The `private.release_deferred_drawing_extractions` trigger exists only in
  #874, so it isn't audited here.

## Enforcement

- `scripts/check-lock-order.mjs` prints the sequence for each audited
  function. It fails on any inversion that isn't in `KNOWN_INVERSIONS`. It
  also fails if a listed function no longer inverts, so each fixing PR must
  remove its entry.
- `scripts/check-lock-order.test.mjs` runs the check against the repository
  in the normal Vitest suite. It isn't wired into a CI workflow.
- The check is static and conservative. It can't see dynamic SQL or locks
  taken by triggers. The two-session dblink tests (redesign PR 2 onward) cover
  real interleavings.
