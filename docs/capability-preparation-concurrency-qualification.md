# Immutable preparation concurrency qualification

This is a source-only qualification plan, not SQL execution evidence. Run only after a separately authorized disposable-fixture checkpoint. Do not add these cases to the existing 28-assertion runtime suite or change its inputs.

Use the reviewed persistent-psql harness topology: one coordinator and two prestarted actors using the same already-authorized socket/database/role. Record three distinct backend PIDs, actual current/session identity and socket transport. Actors use independent autocommit transactions. Coordinator acquires advisory transaction lock `(591,1)` and observes both exact actor PIDs blocked by it before releasing. No sleep alone counts as overlap evidence. SQL failures require captured SQLSTATE from a completed SQL operation; process exit, timeout or framing failure is a harness error. Read-back observations run after both results are captured.

| Race | Inputs and outcome evidence |
| --- | --- |
| Duplicate claim preparation | Same immutable claim twice. Both overlap. Exactly one `created`, one `existing`; both retain identical payload. One retained identity; zero canonical window/revision allocation. |
| Changed claim payload | Same request identity, different completion keys. Exactly one insert; other rejected; winning row equals the winner's original envelope. No partial reservation for loser. |
| Shared completion identity | Distinct request identities with the same completion key. Exactly one insert; other rejected. Different request identities with distinct completion keys at the same window are allowed by the updated contract and must remain separately discoverable. |
| Duplicate completion preparation | First prepare claim, then obtain a real canonical claim/fence. Concurrent identical completion envelopes yield one created/one existing, one original retained payload, no observation append. Wrong owner/fence never survives. |
| Duplicate attention preparation | Identical evaluation key/envelope yields one created/one existing. Changed payload under the same key yields one winner/one rejection. No CAS or outbox mutation. |
| Numeric cursor ordering | Hold the serialization lock while both actors attempt distinct preparation identities at one discovery scope. Confirm overlap. After both commits, each inserted cursor is positive canonical bigint text. Page in numeric order with limit one, preserving original input and last delivered cursor; lookahead determines `hasMore`. Never return a cursor based on sequence/MAX state. |
| Commit visibility and pagination | Actor A inserts while retaining the serialization lock inside a controlled transaction. Actor B attempts a second insertion and is demonstrably blocked. A's row is invisible before A commits; B cannot reserve a preceding or hidden lower cursor. After A commits and B finishes, traversing pages sees both exactly once. Run for claim discovery and attention discovery. |
| Rollback gap | Actor A allocates/inserts then rolls back; B waits on serialization lock and commits. The gap is allowed; page returns only committed B and never a phantom A cursor. Sequence CACHE 1 and no direct sequence privileges are checked independently. |
| Replay after authority changes | Retain exact completion and attention, then advance canonical time/state through existing APIs or controlled fixture-only setup. Replay preparation returns original bytes/semantic JSON without restoring probe authority, changing canonical state or bypassing canonical completion/CAS rejection. |

Each race needs separate bounded result receipts, exact inputs, original and changed identity values, per-session stdout/stderr, SQLSTATE, PID overlap observations, table counts and final TAP assertions. Explicitly preserve object values, array order, timestamp spelling and nulls while allowing JSON object member reordering. Different attention evaluations at the same scope and expectedVersion must coexist: no version-only uniqueness.

Cleanup must prove every actor backend and in-container process exited before removing helpers or fixture resources. Killing the host Docker CLI alone is insufficient. Retain pre/post owned-resource inventory and explain any unrelated infrastructure identity changes before another runtime checkpoint. Operational rollback disables consumers/revokes new service RPCs and keeps retained audit rows; the synthetic test transaction rolls back its own rows/helpers, allowing sequence gaps. No credentials, HBA, role, authentication or browser-sandbox changes are part of this plan.

The standalone SQL fixture additionally owns the non-concurrent boundary cases from RSR-1: 101 retained claim identities and 101 attention evaluations, 100-row lookahead pages, final one-row pages, empty exhaustion, exact discovery isolation, and lossless JSON-string cursors above JavaScript's safe integer range. Its exclusively disposable owner uses transactional `ALTER SEQUENCE ... RESTART` inside the outer fixture transaction; `finish()` precedes the outer `ROLLBACK`. No `setval`, service sequence grant, production reset or recovery action is introduced. These checks do not substitute for concurrent publication-order proof.
