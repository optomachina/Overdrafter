## Problem (verified by reading the migrations in order and by execution)

- **3f.** `api_update_client_part_request` was defined in 20260310110000, 20260313143000, 20260313150000, 20260316170500, 20260402120000 and 20260408120000; OVD-736 changed only its grants. The 20260316170500 version wrote `spec_snapshot.fieldSources[field] = 'user'`. The April versions (20260402120000 and 20260408120000) record corrections only in `spec_snapshot.projectPartProperties.overrides`. `api_auto_approve_job_requirements` (latest definition 20260317013000) decides ownership only from `fieldSources`. Fields with no `fieldSources` entry count as `'auto'`, and any auto field is refreshed whenever `drawing_extractions.updated_at > approved_part_requirements.updated_at`. So when a user saves while an extraction is pending (or being retried), the extraction that finishes later overwrites description, part number, revision, finish, quoteDescription and quoteFinish. Finish is sent to Xometry and SendCutSend (docs/quote-scope-trace.md).
- **1b-b.** A drawing is attached to an existing job in four steps: upload (`uploadFilesToJob`), `api_reconcile_job_parts` (its upsert sets `parts.drawing_file_id`), then `api_request_extraction`. The callers are `use-client-part-controller.ts`, `use-client-project-controller.ts` and `uploads-api.ts`. The legacy `api_attach_job_file` raises `legacy_file_attach_unavailable`. `api_request_extraction` queues `extract_part` only for parts with no `drawing_extractions` row. A part already extracted CAD-only (the worker writes `extractor_version = 'worker-sim-v1'` when no drawing was staged) is therefore never extracted from its new drawing.

## Draft a: what auto-approve now does

### Ownership (3f): option (b) only, and why not (a)

```
user_owned(field) := fieldSources[field] <> 'auto'             -- legacy, unchanged
                     OR projectPartProperties.overrides ? field  -- new
refresh(field)    := not user_owned and extraction newer and not review_needed
```

Each "refresh from newer extraction" branch tests `refresh(field)`. The override keys used by the update/reset RPCs are `description`, `partNumber`, `revision` and `finish`, the same names auto-approve uses.

- (b) also protects overrides that are already stored, with no data backfill.
- The legacy term is kept so that ownership written by `api_approve_job_requirements` (internal approval, which sets all four to `'user'` and replaces `spec_snapshot`) and by the March client RPC is not weakened (harness S7).
- Reset is not changed. `api_reset_client_part_property_overrides` removes the override key, so the field becomes auto again (pgTAP A3/A4). A legacy `fieldSources = 'user'` is not touched by reset today, and it still is not.
- Option (a), writing `fieldSources` in the update RPC, was rejected. Reset does not clear `fieldSources` (and must not be changed), so (a) would make every override sticky through a reset. It would also not protect overrides already stored, and it would replace a 300-line SECURITY DEFINER RPC.
- The `fieldSources` and `fieldOverrides` values written back by auto-approve are unchanged (still the legacy provenance), so the draft makes no new value sticky.

### R1 (high): editor defaults follow a refreshed field

When `refresh(field)` is true, auto-approve also writes the refreshed value into `spec_snapshot.projectPartProperties.defaults[field]`: `description` gets `quoteDescription` (else `description`), `finish` gets `quoteFinish` (else `finish`), `partNumber` and `revision` their column values. These are the same expressions `seed_project_part_property_defaults` would compute from the refreshed row. It changes only an existing `defaults` object; when there is none, the update RPC seeds it later from the refreshed columns, with the same result. Reset is not changed: it still removes the override key and resolves to the default, which is now the refreshed value. Without this, after CAD-only extraction, a save (which seeds CAD-only defaults), a drawing attach and its extraction: a reset wrote the stale CAD-only value (and auto-approve never repaired it, because the requirement was then newer); the next unrelated save turned every refreshed field into an override (user-owned under draft a); the editor showed stale defaults. pgTAP D3, D4, D5.

### M1 (review r2, medium): a reset after a save-while-pending returns the drawing value

Sequence (verified on a real Postgres 17.11 schema): the user saves while extraction is pending; the first save seeds the editor defaults with no requirement and no extraction, so `defaults.description` is JSON null. The extraction completes; the correction is kept (owned). The user resets the field: the override key is removed, the field resolves to the null default, and the column keeps the old value. The field is auto by ownership but the drawing value is never applied until another extraction runs. Finish behaves the same, and finish is sent to Xometry and SendCutSend.

Fix (option (a) of the earlier notes): in the defaults block, when the field is owned through an override (`projectPartProperties.overrides` has the key), the extraction is newer than the requirement, the field is not flagged `reviewNeeded` and the extraction has a non-empty value for it, `defaults[field]` is set to that value. The column and the override are not changed, so the correction still survives (pgTAP A2, M1). A reset then resolves to the drawing value at once (A3b, M2). The extracted value is the extraction's own: `quoteDescription` else `description`/`desc`; `partNumber`/`pn`; `revision`/`rev`; `quoteFinish` else `finish.normalized`/`raw`/`raw_text`. It never falls back to the requirement's value.

What it deliberately does not do:
- A field owned only through the legacy `fieldSources` (no override key) keeps its default (pgTAP V2). Reset cannot clear a legacy owner, and `api_reset_client_part_property_overrides` recomputes every field from defaults and overrides, so a moved default would overwrite that field's column on the next reset of any other field.
- A stale extraction (V1), a missing value, and a review flag (V2) change nothing.
- Material is not covered: the requirement column wins the material coalesce, so even another extraction does not refresh a stored material, and the only extraction-driven change stays the placeholder replacement (R2).

Trade-off, accepted: a later save whose override equals the new default (the user retyped the drawing's value) drops that override, so the field becomes auto again. The value is the same.

### Lock order (revision 7, Codex high)

Sequence (reproduced with two sessions on the revision 6 bytes, R3 and R4 of the concurrency file): a client save is in flight (written, not committed) when auto-approval starts. Auto-approval read the requirement row without a lock, so it saw the version before the save; it then blocked on the part row the save had updated, and when the save committed it continued with the stale read: the extraction was newer than that stale requirement and the stale snapshot had no override keys, so description, part number, revision and finish were refreshed from the extraction and the upsert wrote the old `spec_snapshot` back, dropping the overrides. A reset had the reverse problem (S3): it read the editor defaults before an auto-approval committed and wrote them back afterwards.

Fix: every path that writes the approved requirement of a part takes the row locks of one job in this order, and the first before it reads anything it writes back (also stated in the header of `20261020002126`):

1. the `public.jobs` row (`FOR NO KEY UPDATE`: an `UPDATE` of the row takes the same mode, and neither blocks the `FOR KEY SHARE` of a foreign-key check, so inserts that reference the job are not serialized);
2. the job's `public.parts` rows;
3. `public.approved_part_requirements` rows;
4. `public.drawing_extractions` rows;
5. `public.work_queue` rows.

- `api_auto_approve_job_requirements` reads its job row `FOR NO KEY UPDATE` as its first statement (lock 1), then works through 2 to 4 per part and only reads `work_queue`.
- `api_update_client_part_request` and `api_reset_client_part_property_overrides` are not redefined. Both call `load_editable_project_part_context(p_job_id)` before they read anything (pinned in Vitest), so that function, redefined in migration a, takes lock 1 after its access checks and re-reads the job under it; the part, requirement and extraction reads that follow see what a concurrent auto-approval committed, and the RPCs' own writes all happen under lock 1. A row lock is not allowed in a `STABLE` function, so it is now `VOLATILE`; its callers are volatile RPCs that write. The body is otherwise verbatim from 20260402120000 (pinned), `search_path` becomes `pg_catalog, public` (the security-definer lint), and the OVD-736 ACL is restated (service_role only). This was the least invasive place: the two RPCs are 300-line SECURITY DEFINER functions, and the loader is their single shared entry.
- `api_request_extraction` (migration b) keeps its advisory lock, then takes lock 1 before `api_reconcile_job_parts` locks parts (lock 2), then lock 5 (below). Before, it locked parts first and the job last; with auto-approval now taking the job first, keeping that order would have been an inversion (a deadlock between an attach and an extraction finishing).
- The worker's task settlement and the new release trigger touch only `work_queue` rows (5). The triggers on these tables (`touch_*_updated_at`, the part deadline history, the canonical version assignment) only write the row being changed or private history rows, so they add no edge.
- Not conforming, unchanged: `api_approve_job_requirements` (internal staff approval) does not take lock 1 and locks requirements, parts, extractions and then the job. It already used a different order from auto-approval on main (requirement before part, against part before requirement), so a deadlock between the two was possible before and is still possible; PostgreSQL detects it and aborts one transaction. It is a staff action and out of OVD-979; noted under "What is NOT changed". `api_confirm_part_deadline` locks only the requirement row and adds no edge.
- What a waiting save sees: a save that starts while auto-approval runs waits at lock 1, then reads the requirement auto-approval committed. A save in flight when auto-approval starts makes auto-approval wait at lock 1, and auto-approval then reads the save's override keys and keeps the corrections (R3, R4). Neither waits for long: both run in one RPC transaction.

### Per-claim completion evidence (revision 7, Codex medium; closes "Still open" item 4)

Revision 3's exemption (a running `drawing_attached` task whose part holds a non-CAD-only row is finishing) assumed that the row was written by the running task. Since revision 4 a retried attach starts with the row its failed attempt stored, so the retry counted as finishing from its claim, and another part's auto-approval could roll the job to `ready_to_quote` while the retry was unfinished (RV1, C1 on the revision 6 bytes).

Fix, without a worker change:
- The exemption needs `stored.updated_at > queue.locked_at`: the row was written after this claim began. `api_claim_next_task` sets `locked_at = now()`, and the worker's `drawing_extractions` upsert sets no timestamps, so the touch trigger stamps `updated_at` with the time of the worker's write (a separate, later transaction). A tie is not evidence (RV1 pins it; in production the claim and the write are separate transactions, so `>` and `>=` only differ in the one-clock test).
- The set of finishing tasks is read at the start of auto-approval, before the loop. The loop's own status updates (`approved`, or `needs_review`) are stamped by the same trigger, and an earlier cut that read the evidence after the loop counted every run's own write as the worker's.
- The confounder revision 5 found (another part's auto-approval updates `drawing_extractions.status` for every part of the job, and the stamp moves `updated_at` past `locked_at`): auto-approval no longer changes the status of a row that is older than (or as old as) the claim of a running `drawing_attached` task of its part. That running claim replaces the row, and its own auto-approval sets the status (RV2, C2). Nothing else changes for that part in that run (the requirement is still refreshed from the row, as before).
- The trusted reuse path writes no worker upsert. It now stamps the target's row (`updated_at = now`) when the target has a drawing, after the copy, so the auto-approval of the same claim sees a row written during the claim: a replaced CAD-only row was already stamped by the conflict clause, a kept row (stored by a failed attempt) and a copied row (which carries the source's timestamps) were not (RU5b). Side effect, accepted: a copied row now reads as newer than a requirement saved while the extraction was pending, so auto-approval refreshes the target's non-owned fields from it, as it does after a worker extraction.
- Residual: `api_approve_job_requirements` (staff) also sets `drawing_extractions.status`; if a staff member approves the job while a retry runs, the stamp counts as evidence for that retry until it stores its own row. The rollup is then wrong at most until the retry's own run.

### Provenance keys (Codex 2, medium): `fieldSources` was rebuilt from four keys

`api_auto_approve_job_requirements` merges `fieldSources` and `fieldOverrides` into `spec_snapshot` with `||`, which replaced each object with its four rebuilt keys. R2's guard reads `fieldSources.material`; the first run honoured a stored `'user'` and then dropped the key, so the next run (any later auto-approval of the job) replaced the placeholder with the extracted material, with no newer extraction needed (verified: pgTAP H1 fails on revision 1). Each object is now `existing object || the four rebuilt keys` (an existing non-object value is treated as empty). The four legacy values are written exactly as before, so no refreshed value becomes sticky. Nothing in the repository writes `fieldSources.material` today (the importers write the four keys); the guard and its provenance had to survive for the day something does.

### R2 (medium): the 'Unknown material' placeholder no longer blocks an extracted material

A CAD-only auto-approval of a `manufacturing_quote` job stores `material = 'Unknown material'`. Because the requirement column wins the material coalesce, a later drawing extraction never replaced it. Now, when the requirement material is exactly `'Unknown material'` (trimmed), material is not user-owned (no `overrides.material` key, `fieldSources.material` absent or `'auto'`) and the extraction has a material (`material.normalized`, `raw` or `raw_text`), the extracted material replaces the placeholder. Without an extracted material nothing changes (the placeholder stays, also for a job that no longer requires material). The editor default follows (as R1). A user-stored `'Unknown material'` override is kept (pgTAP E1); D1 covers the replacement.

### R3 (medium, blocks): a drawing-attach extraction never fills tolerance

Decision: the conservative option. For a part that has any `extract_part` task with `payload.reason = 'drawing_attached'` (queued only by draft b), auto-approve keeps `tightest_tolerance_inch` at the requirement value instead of `coalesce(requirement, extraction)`. For a CAD-only part that value is null.

- Why: until OVD-976 ships, a millimetre drawing is stored as inches, and a newly non-null tolerance could pass the OVD-683 Xometry gate at a looser tier (and could change SendCutSend eligibility if vendors were recomputed). Null fails closed today, so keeping null is the safe default.
- Product effect: after an attach, description, part number, revision, finish and material fill in from the drawing, and auto-approve leaves tolerance at the stored value (null for a CAD-only part). `applicable_vendors` is not recomputed (unchanged rule: a stored non-empty list is kept).
- **Limit (review r1, F1): the next save can still adopt the drawing tolerance without the user choosing it.** Two paths, both on main and outside these drafts: (1) the client draft falls back to the extraction tolerance when the requirement has none (`src/features/quotes/utils.ts` `buildRequirementDraft`), so an unrelated save sends 0.1; (2) when the user never saved before the attach, `api_update_client_part_request` seeds `defaults.tightestToleranceInch` lazily from the extraction (20260408120000 `seed_project_part_property_defaults`), and a null override resolves to that default. The reviewer's harness shows the column becoming 0.1000 after an unrelated save in both cases (save sends 0.1, or sends null with override `{tightestToleranceInch: null}`). Only when the user had saved before the attach and the save sends null does tolerance stay null. So R3 is defence in depth, not a mitigation: OVD-976 deployed first is the real one, and OVD-984 removes path (1).
- Not done (considered): pinning `defaults.tightestToleranceInch` to the requirement value on an attach. When a defaults object already exists, the first save already seeded that key (null for a CAD-only part), so the pin changes nothing. Path (2) has no defaults object; creating a partial one would change what the client editor shows as defaults for every other field until the next save. Not worth it ahead of OVD-976.
- Scope: only the attach path. A drawing uploaded together with the part still fills tolerance exactly as today (pgTAP A5); that path carries the same pre-OVD-976 risk on main and is OVD-976's to fix.
- Decided (Blaine, 2026-10-18): lift this rule in a follow-up migration once OVD-976 is deployed and verified (one `case` branch). It is not lifted in this change, and the follow-up is not part of these drafts. It is deliberately not tied to OVD-976's output shape, which is not merged.
- pgTAP D2.

### R4 (medium, blocks): status rollup never leaves a quoting-or-later state

`job_status` (20260303101500) is `uploaded, extracting, needs_spec_review, ready_to_quote, quoting, awaiting_vendor_manual_review, internal_review, published, client_selected, closed`. Existing transition rules: `api_request_quote` sets `quoting` (20260812044000); cancelling a quote request maps `quoting` to `ready_to_quote` and keeps `client_selected`/`closed` (20261002182714); the request-quote path (20260402100000 and earlier versions) treats `internal_review, published, client_selected, closed` as already received for a part with an existing quote run. Draft a's rollup now updates a job only when its status is `uploaded`, `extracting`, `needs_spec_review` or `ready_to_quote` (an allow-list, so a future enum value is left alone). Draft b: see below. pgTAP Q1 to Q3 (`published`, `client_selected`, `closed`).

This also fixes a case on main: a correction saved while extraction is pending creates the requirement, so the user can request a quote (`quoting`) before the extraction finishes; the completing extraction then moved the job back to `extracting`/`ready_to_quote`. It now stays `quoting`.

What happens to quoted fields when an extraction completes after quoting started: the requirement is refreshed (non-user-owned description, part number, revision, finish, the material placeholder), as pgTAP Q1 to Q3 show. Quote scope is immutable per OVD-345 (20260812041000): the worker builds each lane's `scope_snapshot` (including requirement description, finish, material, tolerance, and the CAD/drawing file ids and hashes) when the vendor task runs (`worker/src/quoteScope.ts`, `worker/src/index.ts` vendor path) and registers it once with `api_register_quote_request_lane`, which refuses a different fingerprint for an already registered lane ("Quote lane was already registered with a different immutable scope."). So offers and registered lanes keep the spec they were quoted on. A vendor task of the same run that has not dispatched yet would register the refreshed values, so one run can carry mixed scopes. That is the same as a user edit or the attach itself during quoting on main (the attach changes `drawing_file_id`, which is in the scope, without draft b). Decided (Blaine, 2026-10-18): keep refreshing non-owned fields on jobs in quoting or later; auto-approve does not skip field refreshes there (see "Decisions").

### Job status after the worker's run (Codex 1, medium, revision 3)

The worker calls auto-approve while its own task is still `running` and marks the task completed afterwards (`worker/src/index.ts`: the extraction path and the trusted-reuse path both run `autoApproveJobRequirements` before `markTaskCompleted`). The rollup therefore counted the task it was called from as pending and wrote `extracting`, never `ready_to_quote` or `needs_spec_review`. Revision 2 documented this as an observation; it matters for the attach because draft b moves a pre-quote job to `extracting` when it queues the task, and nothing moved it back, so a ready job showed "Processing in background" (`client-workspace-state.ts`) after its drawing was extracted. Reproduced on a real schema with the worker's order (the pgTAP helper used to complete the task first, which hid it).

Change: a queued or running `extract_part` task counts as pending unless it is running, has `payload.reason = 'drawing_attached'` and its part already holds a stored extraction that is not CAD-only (`extractor_version not like 'worker-sim-%'`). Such a task has written its result (the worker writes the extraction row before it calls auto-approve; the reuse path replaces the CAD-only row with the source's, draft b) and only its queue row is still to be completed. What still counts: every queued task (including one requeued after a worker crash with its extraction already stored, W5), a running attach task whose part still holds the CAD-only row (W2, another part's run can call auto-approve meanwhile), and any running first-extraction task. The `reason` comparison is `is not distinct from`: with a plain `=`, a task without a reason makes the whole `not (...)` null and the first-extraction task silently drops out of the count too (found by the W6 case while writing this; the Vitest pin rejects the plain form).

Deliberately not widened: the first extraction of a new part keeps the status flow of main, so its job still ends `extracting` after the worker's run (pgTAP W6; the same latent gap exists on main for every new upload and for a new part on a quoted job). Fixing it changes how every job moves after its first extraction, which is outside OVD-979 and was not analysed here (see "Still open").

Alternatives rejected: reordering the worker (completing the task before auto-approve) changes production behaviour before any migration is applied and breaks the "inert until applied" property of this PR; a trigger on `work_queue` that rolls the job up on completion adds a new object on a hot table and a new SECURITY DEFINER function for what two predicates do.

### Retried failures (Codex 2, medium, revision 3)

`api_request_extraction` retries a failed task by inserting a new task and keeping the failed one (its dedupe looks only at queued and running tasks), and the rollup counted every failed `extract_part` task of the job. After a failed drawing task and a successful retry through the RPC, the failed row therefore kept the job in `needs_spec_review` for good. The revision 2 test hid this: it set the original failed row back to `queued`, which the RPC never does (the worker only requeues a task for a retryable error, from `running`, never from `failed`).

Change: a failed task does not count when a later task of the same part (`created_at` greater, same job) is queued, running or completed. A failure followed only by failed or cancelled tasks still counts, and so does a failure whose only later task belongs to another part (pgTAP Z1, Z2, Z2b). Several failures of one part are all replaced by one later success (Z3, Z4); the failed rows stay on record (F4b). The failed rows are not rewritten and `api_request_extraction` is unchanged. This follows the "a later task replaces an earlier one" reading of the client projection, which takes the latest `extract_part` task of a part by `created_at` (`20261011170000`), except that a cancelled or failed later task is not an outcome here and so does not hide a failure. It also applies to a failed first extraction that was retried, where main has the same gap (the failed branch is only reachable on main when no `extract_part` task of the job is queued or running at the call, which the worker never does because its own task is running).

What the worker's order means for failures: a failed task is marked by `markTaskFailed`, which does not call auto-approve, so after a failed attach the job stays `extracting` until the next auto-approval run for it (another part's extraction, or the retry's own), and that run rolls it up. The "needs_spec_review after a failed attach" of decision 3 is therefore reached through the next run, as pgTAP F1 and Z1 to Z2 exercise it, and a retry that succeeds replaces it (F4, Z3).

## Draft b: what request_extraction now does (1b-b; depends on draft a)

`api_request_extraction` now also queues a part when all of the following hold:

1. it has a `drawing_file_id`;
2. its extraction row has `extractor_version like 'worker-sim-%'`;
3. no `extract_part` task for the same part with `payload.drawingFileId` equal to the current drawing has completed.

The existing "nothing queued or running for this part" dedupe applies to both branches. The new task's payload adds `reason: 'drawing_attached'` and `drawingFileId`; the worker merges payloads on completion (`worker/src/queue.ts` `mergePayload`), so the completed-task guard works. The payload for a never-extracted part is unchanged byte for byte. A per-job transaction advisory lock, taken after the access checks, serializes concurrent calls. It takes no row lock, so it cannot invert the parts-then-jobs lock order that auto-approve uses. When the worker completes, auto-approve (draft a) refreshes the auto fields from the drawing and keeps user-owned ones (pgTAP B5).

Job status (R4): a request that queued at least one never-extracted part sets `extracting` exactly as on main (the behaviour for a new upload is unchanged, including on a quoted job). A request that queued only `drawing_attached` tasks sets `extracting` only for a job in a pre-quote state (pgTAP B1b); a job in quoting or later keeps its status and the task still runs (Q1 to Q3). Keeping the new-upload behaviour was deliberate: changing how a new part on a quoted job moves the job is outside OVD-979 and was not analysed here (listed under "Still open").

Not re-queued: rows from other producers (`'v1'` default, the importers `dmrifles-import-v1` and `spreadsheet-import-v2`, the pdf extractor) unless a failed or cancelled attach task for the current drawing exists (revision 4, below), and a part with no drawing. The existing `ovd723_export_control_upload_block.sql` assertion ("extraction queues nothing for a part that already has an extraction") uses a `'v1'` row, so it still holds (pgTAP B7, harness S5).

### Trusted reuse (Codex 1, medium, revision 2)

When the attached CAD + drawing package equals a complete version elsewhere in the organization, `handleExtractTask` does not extract: `api_resolve_trusted_part_intake` returns `existing_version`, `api_reuse_trusted_part_version_artifacts` copies the source's extraction and previews, and the task completes. The copy used `on conflict (part_id) do nothing`, so a part that already held its CAD-only extraction (`worker-sim-v1`) kept it, completed the task and, because the draft's completed-task dedupe skips a drawing that already has a completed task, was never extracted from its drawing. Verified on a real schema (pgTAP RU2, RU3 fail on revision 1, RU4 passes: the part stays CAD-only and nothing is queued again). Before this change nothing was queued at all for such a part, so it is not a regression, but the attach feature did not work for it.

Fix: `api_reuse_trusted_part_version_artifacts` is replaced in draft b, verbatim from 20260812042000 except for the conflict clause of the `drawing_extractions` insert: it now updates the row (extractor version, extraction, confidence, warnings, evidence, status, `updated_at`) when the target part has a drawing and its current row is CAD-only (`extractor_version like 'worker-sim-%'`). Any other existing row is kept (RU5), a part without a drawing is left alone (RU6), and a missing row is inserted as before. After the replacement the row is no longer CAD-only, so the queue branch stops matching and nothing loops (RU4). The worker's auto-approve that follows sees an extraction newer than the requirement and refreshes the auto fields from it, as for any extraction (RU3). The function stays service_role only, `SECURITY DEFINER`, `search_path = pg_catalog` (G6, and a Vitest text pin that the rest of the body equals 20260812042000). It lives in b so that one file carries the whole drawing-attach path and so the existing Sonar duplication exclusion for the two OVD-979 migrations covers it.

Closed in revision 5: when the source version's own row is also CAD-only (its extraction ran before its drawing existed and was never redone), this revision-2 change copied that CAD-only row over the target's, so the target still had no drawing data. The reuse no longer copies a CAD-only row onto a part that has a drawing; see "CAD-only source" below.

### Retry after partial persistence (Codex, medium, revision 4)

The worker stores the extraction row first. In `handleExtractTask` the order is: the `drawing_extractions` upsert, the drawing preview upload and rows (`persistDrawingPreviewAssets` throws on an upload or insert error), the CAD preview (errors there are caught), `autoApproveJobRequirements`, the audit event, `markTaskCompleted`. Only `CanonicalArtifactsPendingError`, `ExportControlLookupError` and `ExportControlStepScanRetryableError` requeue the same task for `extract_part`, and each is thrown before the upsert; any other error after it marks the task `failed`. For a drawing attach that left `drawing_extractions` holding a `worker-pdf-v3` row, a failed task naming the drawing, a requirement still holding the CAD-only values and no previews. The revision 3 predicate (CAD-only row, no completed task for the drawing) excluded that part, so `api_request_extraction` returned 0 for as long as the user waited, and the failed task pinned the job at the next auto-approval run (decision 3). pgTAP PP0 pins that state.

Change: the second queue branch now reads "the part has a drawing, no `extract_part` task for this drawing has completed, and either the row is CAD-only or an `extract_part` task of the same job and part with `status in ('failed', 'cancelled')` names the current drawing in `payload.drawingFileId`". The existing "nothing queued or running for this part" dedupe applies as before, and the payload of the retry is the `drawing_attached` payload (an extraction row exists), so one completed retry ends the retries.

- Both unsuccessful statuses: a cancelled task is as unsuccessful as a failed one (the rollup already treats a cancelled retry like a failed one, Z1), and a CAD-only part with a cancelled task is already queued again by the first alternative. PP4 covers a cancelled retry next to the failure and PC1 a cancelled task with no failure at all, the only case that tells `('failed')` from `('failed', 'cancelled')`.
- Matched by `drawingFileId`, not by `reason`: only attach tasks carry it, a first-extraction task never does, and it makes the retry per drawing. A failed task that names another drawing queues nothing (PV1; replacing a drawing after a drawing extraction is still not re-queued, see below).
- Once a task for the current drawing completed, nothing is queued again, whatever failed or was cancelled before it (PP5b, PP6): the failed rows stay on record and stop counting in the rollup when the retry is queued (revision 3 rule).
- The retry replaces the stored row with the worker's upsert, re-persists the previews (the worker deletes the part's preview rows and inserts them again, with the storage upload overwriting), and auto-approval refreshes the requirement from the newer extraction (PP5: description from the drawing, job `ready_to_quote`). If the identical package exists elsewhere by then, the retry takes the trusted-reuse path, which keeps a stored non-CAD-only row (RU5) and fills missing previews (`on conflict do nothing`).

Not changed: a first extraction (a part uploaded with its drawing) that fails after storing its row is not retried by this RPC either, because the RPC only looks for parts without an extraction row; main behaves the same and that is outside OVD-979. A task stuck `running` is the reaper's, not this function's.

### CAD-only source (Codex, medium, revision 5)

Premise, checked in the worker and the migrations. `handleExtractTask` calls `api_resolve_trusted_part_intake` first, which runs `private.assign_canonical_part_version`; the version of a package belongs to the first placement that holds it (`part_versions.source_part_id`), and the same assignment also runs when a drawing hash is registered or a drawing is attached (trigger on `parts`). The extraction row is written much later (`runDrawingExtractionForTask` stages the drawing, reads its text and calls the model; the upsert comes after, and any error before it ends in `markTaskFailed`). So a source placement K whose attach task fails between the two owns a complete version, still holds the `worker-sim-v1` row from before its drawing existed, and has a failed task and nothing queued or running, which is exactly the state in which the reuse's pending checks let a copy through. Another placement of the same package resolves to `existing_version` with K as source, `api_reuse_trusted_part_version_artifacts` copied K's CAD-only row (over the target's own CAD-only row since revision 2), returned `artifactsReady` true, the worker auto-approved and completed the target's task (its payload names `drawingFileId`), and rule 3 then never queued the target again. The target looked finished but had never read its drawing.

Fix, in the reuse function only: after the two pending checks and before the copy, a part that has a drawing (`v_target.drawing_file_id is not null`) whose source row is `worker-sim-%` gets `result` `source_cad_only`, `artifactsReady` false and `extractTargetIndependently` true, and nothing is copied. The worker reads only those two flags: `!artifactsReady` with `extractTargetIndependently` falls through to `runDrawingExtractionForTask`, the path it already takes when the source has no extraction (`source_unavailable`), so the target is extracted from its own drawing (`worker-pdf-v3`) and its previews are persisted by that run. The cost is one model run for that target, as for any part without a reusable source. The new `result` string is not read anywhere else; the worker-compatibility fixtures `catalog.sql` and `service_role.sql` still pass (207 and 95).

- The target's own row does not matter, on purpose. A target with a CAD-only row (the review's case, CS1 and CS2), a target with no row at all, a part uploaded together with its drawing (CS4, which also closes the revision 2 "Not changed" case for new parts), and a target that already stores its own drawing extraction (CS5) all extract again. The last one is the retry after partial persistence of revision 4: reusing would keep the stored row but copy no previews from a source that has none, so the previews would never finish; extracting again re-persists them.

### Unfinished source (Codex, medium, revision 6)

Premise, checked in the worker and the migrations. `handleExtractTask` stores the `drawing_extractions` row (upsert) before anything else that can fail: `persistDrawingPreviewAssets` is awaited next with no `try` around it, then the CAD preview (which is wrapped and only logs), then `autoApproveJobRequirements`, the audit event and `markTaskCompleted`. A throw at any of those steps reaches the handler's `catch`, which rethrows to `processClaimedTask`; unless the error is one of the retryable kinds (a canonical-artifacts wait, an export-control lookup or STEP-scan retry), the task ends in `markTaskFailed`. So a source placement whose task fails after the upsert has a drawing-derived `worker-pdf-v3` row (revision 5's CAD-only check does not apply to it), possibly some or none of its preview rows, a `failed` task, and nothing queued or running, which is the state the reuse's pending checks let a copy through. A target of the same package copied the row and whatever previews existed, the worker auto-approved and completed the target's task (its payload names `drawingFileId` when it is an attach), and the completed-task guard of `api_request_extraction` (rule 3) then never queued it again: the target stayed without its previews.

Fix, in the reuse function only: after the CAD-only return of revision 5 and before the copy, the source must have an `extract_part` task of its own part and job (`job_id` is in the predicate so the lookup can use `work_queue_job_task_type_idx`) with status `completed` such that no `extract_part` task of the same part with status `failed` or `cancelled` has `created_at >=` it. If there is none the reuse returns `result` `source_extraction_unfinished`, `artifactsReady` false and `extractTargetIndependently` true and copies nothing. The worker reads only those two flags (the new `result` string is read nowhere else; the worker-compatibility fixtures `catalog.sql` and `service_role.sql` still pass, 207 and 95), so it falls through to `runDrawingExtractionForTask` exactly as for `source_unavailable` and `source_cad_only`: the target is extracted from its own files and its previews are persisted by that run.

- The producing task is the source's latest finished task. A source that completed a CAD-only extraction and then failed its drawing attach (RF0) has a completed task and a later failed one: untrusted, although a completed task exists. A failed task followed by a retry that completed is history and the source is trusted again (RF4); the retry is queued by `api_request_extraction` (rule 7), so a source heals itself as soon as anyone asks for extraction for its job.
- Order: the check follows the pending checks, so a source whose retry is queued or running is waited for rather than extracted a second time (RF3b), and it follows the CAD-only return and precedes the copy.
- `failed` and `cancelled` both count (an `extract_part` task cancelled by hand while it ran may have stored the row and none of the previews; the worker's own cancel paths and the provider kill switch act on vendor tasks, not on extraction; RF2), as in the retry rule of revision 4 and the roll-up of part a.
- Ties count against the source (`>=`): a completion and a failure created at the same instant are not ordered, and an unordered pair is not evidence that the extraction finished. In production tasks of one part are serialized by the dedupe (nothing is queued while a task is queued or running), so the creation times differ; the tie only arises in the single-clock test transaction (RF7), and the roll-up of part a treats a tie the same way (a failure counts unless a strictly later task replaced it).
- A source with no `extract_part` task on record is not trusted (RF5; trusted again once a completed task is on record, RF6). See the behaviour note in the revision 6 paragraph.
- A package whose source is untrusted extracts once per identical upload until the source is retried or a new canonical source exists; the first target that extracts successfully does not become the source (the version belongs to the first placement). That cost (a model run) is accepted over serving an incomplete package, and it ends when the source's own retry completes.
- The `on conflict ... where v_target.drawing_file_id is not null and ... like 'worker-sim-%'` clause of revision 2 and the early return of revision 5 are kept as written.

### Deferred drawing task (revision 7, Codex medium)

Sequence (D1 on the revision 6 bytes): the CAD-only extraction of a part is claimed before its drawing exists, stores its `worker-sim-v1` row and has not completed; the drawing is attached and `api_request_extraction` runs. The part has a drawing and a CAD-only row, but its task is running, so the queued-or-running dedupe skipped it and the request returned 0. The worker's completion is a direct `UPDATE` of `work_queue` (`markTaskCompleted` in `worker/src/queue.ts`), which calls nothing, so nothing ever queued the drawing.

Fix:
- Intent: such a part gets one `drawing_attached` task at once, deferred: `status` queued, `payload.awaitingTaskId` naming the running task, and `available_at` one hour ahead, so `api_claim_next_task` (which needs `available_at <= now()`, pinned) cannot take it while the running task can still write the part's extraction. The intent is a row, not a payload key on the running task: `markTaskCompleted` writes back the payload it read at claim time, so a key added in between would be lost.
- Release on settlement: a new `AFTER UPDATE OF status` trigger on `public.work_queue` (`release_deferred_drawing_extractions`, function `private.release_deferred_drawing_extractions()`, SECURITY DEFINER, `search_path = pg_catalog`, no EXECUTE for PUBLIC, anon or authenticated) sets `available_at = now` on the deferred task when the awaited `extract_part` task leaves `queued` or `running` for `completed`, `failed` or `cancelled`: the worker's three settle helpers and the reaper all update `status` (pinned). Completion (DF4, D4) and failure (DF6) both release it.
- When it defers: the part has a drawing; it is a never-extracted part or the drawing branch applies (CAD-only row, or a failed or cancelled attach for this drawing, rule 7); no task of the part is queued (a queued task reads the part when it is claimed; the deferred task is itself queued, so a second request adds nothing, DF3); and no task for the current drawing is running or has completed (DF7). A first extraction that has stored nothing yet is deferred behind too (DF8): it may never read the drawing, and the deferred task carries the `drawing_attached` payload (so R3 and the completed-task guard apply to it).
- Race with the settlement: the request locks the job's running `extract_part` tasks (`FOR NO KEY UPDATE`, lock 5) before it decides. A settlement that commits after that waits for the request, and the trigger, running in the settling transaction after the wait, sees the committed deferred row (D2, D4); one that committed before is seen as settled by the insert, which then queues normally.
- Backstop: the hour is only for a missed release (for example a task deferred just before the rollback drops the trigger). The worker's reaper fails any task left running for ten minutes (`reapStaleTasks`), so the awaited task has settled long before the backstop.
- Status: a deferred task counts as queued for the rollup, so the job stays `extracting` until the drawing is extracted (DF5), and for the trusted reuse of a source part it is a pending source (the target waits).
- Cost: a part whose running first extraction did read the drawing (the drawing was attached before the worker staged the part) is extracted a second time from the same drawing, one model run. Telling the two apart needs a payload the worker does not write.
- Not changed: a queued (not yet claimed) task when the drawing is attached still adds nothing; that task reads the part, and the drawing, when it is claimed.
