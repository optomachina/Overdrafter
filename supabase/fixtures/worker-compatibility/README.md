## Pre-existing versus candidate-introduced behavior

1. **Pre-existing, source-derived publication blocker:** the unchanged `api_publish_quote_package` immediately calls `require_verified_auth`, which rejects missing `auth.uid()`, then requires internal membership. Its successful writes also require `published_by`. `service_role.sql` preserves the real no-subject caller and expects `You must be signed in to perform this action.` on both source stages. Runtime must confirm this. Do not add a synthetic user subject or internal membership to its caller.
2. **Pre-existing empty-string timestamp error:** the dispatch parameter is `timestamptz` on both stages. The worker fallback `''` cannot resolve as a valid timestamp and should raise 22007 before dispatch. Explicit SQL null also does not invoke a default; that parameter has no default. These negative-path facts alone do not make a correctly claimed task incompatible.
3. **Candidate source-link dependency changes:** the public publisher definition is unchanged but its helper is replaced by candidate migration `20261002053133_align_selection_and_publication_sources.sql`; expiry behavior also depends on `20261002041305_enforce_quote_selection_expiry.sql`. The paired publication control files create a distinct verified/internal **authenticated** control, with prior matching published requirements and two successful providers, so `p_force=false` is genuinely ready. Baseline expects source-less, ambiguous/sort-ranked, and expired source publication to succeed; candidate expects those paths to reject. Both stages expect sole exact sources, null validity, null summary, exact source links, and normal publication to succeed. These controls expose deliberate tightening without weakening it, and do not manufacture an old-worker success.
4. **Candidate dispatch change:** among the ten RPC definitions, only dispatch authorization changes between the compared trees. Its signature is retained; candidate adds admission/entitlement behavior and changes indirect current-candidate eligibility. `old_scope.sql` exercises genuine result/task/lane/permit/entitlement prerequisites with a current positive control and faithful old-scope rejection. Do not replace the old scope with current server scope just to pass.
5. **Old scope pre-existing incompatibility expected from source:** `old_scope.sql` reproduces the receipt’s exact top-level and requirements key sets, preserves `requestedDeliveryDate` and the unmodified old `specification`, and uses actual trusted staged files. It deliberately omits current destination confirmation. On both trees, an old scope may register a previously unreserved lane, but cannot replace the server-created reserved lane; dispatch should return strict false and `dispatch_staged_scope_changed`. The unchanged sourcing-intent migration already exists in baseline126. Runtime must confirm all outcomes. Separately, `scripts/fixtures/compiled-worker-scope.json` is explicitly retained current-source evidence from `8d8d243`; its fixture already includes destination/confirmationRevision/activeDeadline. It is not the archived worker's full scope and is intentionally not used here.
