# OVD-591 reusable CI qualification

`.github/workflows/ovd591-qualification.yml` is a `workflow_call` job for the existing GitHub Linux capacity. The root integration owner must call it from `ci.yml` and include its result in the required aggregate. This source change does not edit that separately owned workflow. No Docker, SQL, registry or hosted operation was run during source implementation; synthetic command tests do not prove PostgreSQL behavior.

The entrypoint is `node scripts/ovd591-ci-fixture.mjs run "$OVD591_EVIDENCE"`. It requires GitHub Linux run/attempt/SHA identity, a clean exact checkout, and a new evidence directory under `RUNNER_TEMP` outside the checkout. It has a 25-minute command budget, bounded individual commands/output, and a separate two-minute owned-cleanup budget within the 30-minute job. Each run has a random nonce in addition to run/attempt identifiers. No target URL, preexisting container, password or fallback transport is accepted.

The adapter pulls only `public.ecr.aws/supabase/postgres:17.6.1.095`, records the resolved image identity, and rejects an unexpected platform, PGDATA or image volume path. The single exclusively owned container joins one new internal network. It has no published ports, host binds, Docker socket or persistent/anonymous volumes, and is limited to 2 CPUs, 3 GiB, 256 PIDs, a 1536 MiB data tmpfs and 256 MiB temporary tmpfs. The image's own initialization runs unchanged; final PID 1 must be PostgreSQL with the expected version/data path and an accepting socket. A fixture-generated password reaches Docker through a mode-0600 temporary env file outside the uploaded evidence directory, removed immediately after creation and on failure. Container inspection JSON containing environment values is never persisted. No role, credential, HBA or authentication changes are made after initialization.

## Selected baseline, deliberately not full-head

The bare database image does not supply the application schema created by the separate GoTrue and Storage services. This bounded fixture therefore declares the capability-only dependency closure before execution. It never tries a broader migration set and removes failing files:

1. Exact maintained prerequisite statements create the original four-value `public.vendor_name` enum and `private` schema/access boundary. `baselineInputs` verifies each complete statement occurs exactly once in its recorded source migration and retains source/statement hashes. These excerpts are identified as bootstrap prerequisites, never as complete applied migrations. No admin email/customer row or auth/storage stub is copied.
2. Apply the complete unchanged canonical ledger migration `20260911031500`, resolver migration `20260927065514`, and OVD-591 runtime migration `20261002090339`, in that order, with `ON_ERROR_STOP` and per-statement deadlines. Keep stdout/stderr, exact applied path/hash list and failing attempts.
3. Independently verify existing image roles, current/session `postgres` identity, `postgres` database, Unix socket, version, pgTAP availability and initially empty baseline. After application, require all six empty postgres-owned forced-RLS private tables, no policies/direct API grants, all eight exact service-only public RPC signatures with fixed search paths, no extra overloads and denied private helper access.
4. Only successful commands and explicit catalog checks produce the provisioning receipt consumed by the unchanged `ovd591-sql-qualification.mjs`. Its invocation explicitly selects `--concurrency=psql`. It executes the unchanged legacy ledger/RPC and runtime suites, followed by the existing three-session phase manifest and all 28 assertions across six observed-lock races. There is no dblink authentication workaround, suite rewrite, simulated receipt in the production adapter or generic pgTAP replacement.

The existing full-head Supabase CI remains a separate required gate. This fixture does not qualify retention's nine-race protocol, its preparation migration, app auth/storage/bootstrap, PostgREST, provider disposal, supplier access, production's eighteen-migration upgrade or any production deployment. `baselineInputs`, catalog admission, resource argument construction and exact ownership cleanup are exported as narrow reusable source boundaries for the same owner's later separately reviewed fixture; this CLI offers no arbitrary SQL/hook selection.

## Failure and cleanup

Before provisioning, capture container/network/volume IDs. Persist attempted names and exact IDs with owner, source and nonce. Any migration, catalog, transport, TAP, missing receipt or remaining client backend fails the job. The adapter does not retry SQL qualification against a dirty fixture. It observes client backend absence after the harness and removes only exact owned IDs; on failed work, destroying the proven-owned container terminates its remaining backend processes. Network removal requires no attached container, and final inventory must equal the original inventory. A missing/foreign ownership match, uncertain creation acknowledgment, unexpected inventory change or failed removal prevents a cleanup pass.

SIGINT/SIGTERM abort the active command and run cleanup. An `always()` workflow step independently retries only the idempotent owned-cleanup verification using the persisted state; every attempt keeps its own receipt. It never prunes, resets the daemon, edits default networks, removes images, or deletes a preexisting resource. Abrupt runner destruction may prevent cleanup evidence, which must not be represented as observed cleanup. The always-uploaded artifact contains only synthetic SQL/results, safe identities and command outcomes; the generated secret file is outside it. A failed qualification remains failed even if cleanup succeeds.

Independent exact-source review and real hosted execution are required before claiming actual migration/catalog/role results or the six races passed. The old Mac result reached zero race assertions and is not reused as acceptance.
